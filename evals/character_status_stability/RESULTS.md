# Issue #126 상태 전이 검증 기록

현재 상태: producer group 원문 진단2c05b1은6개 case 실행·구조 검증을 완료했으나 발생/종료 근거 혼합과 근거 없는 상세값으로 전체 의미 gate는 실패했다. 새 STATUS JSON{name} 제한·END 근거 분리·관찰 kind 중복 제거 보완을 완료했고 전체 AI 테스트는1167 passed,2 skipped다. 이 최신 코드로 새 원문 진단·합성 안전성·원문1~5화 독립10회는 아직 실행하지 않았다. **최종 검증0/10이며 목표는 미완료다.** 이전 실패·비용과 같은 세션·목표 범위의 반복 검증 승인을 유지한다.

## 범위와 기준

- 이슈: https://github.com/catchhole-soma/catchhole-backend-java/issues/126
- 원격 main에서 분리한 Java `a4a7f9e32e5b17c1e2247b2368f283e223e00284`, AI `868d359076b4acc80304f24401966332def102d1`을 출발점으로 사용했다.
- 원문 1~5화의 bytes를 보존하고 매 화 분석·확정 후 다음 화로 진행했다. 빈 작품에서 독립 실행한다.
- 추출 `gpt-5.6-terra`, 주체 해소·비교 `gpt-5.6-luna`, reasoning `none`을 유지했다.
- 실제 Java 후보 저장·비교 claim·확정 API·Fact·snapshot 경로를 사용한다. 로컬 파일 저장, 가짜 SMS, 세계관 추출 제외, 임베딩 제외가 운영과 다른 부분이다.
- 핵심 판정은 비요른의 물리적 오른발 부상이 4화에 실제 활성으로 확정되고, 5화 회복 근거 이후 같은 인물의 현재 상태에서 끝나며, 이력과 무관한 상태가 보존되는 것이다. 5화의 빈 상태만으로 성공을 판정하지 않는다.
- 독의 완전 해독을 원문 정답으로 강제하지 않는다. 근거와 불확실성을 따로 기록한다.
- 원문·기대값은 제품 코드에 넣지 않았다. 검수 체크리스트와 합성 정답은 모델 입력에 전달하지 않는다.

## 확인한 원인과 수정

1. main의 기존 활성 STATUS 전달과 다중 REMOVE 지원만으로는 관찰 누락을 해결하지 못했다. 회복 수단·재생 문구만 뽑고 뒤의 실제 기능 회복을 놓치면 비교 단계에 종료 근거가 도착하지 않았다. 일반 설정과 별도로 현재 청크 전체의 STATUS 전환을 독립 추출하도록 변경했다.
2. 이름이 없는 1인칭 회차에서 주체를 다른 인물에게 연결하는 실행이 있었다. 바로 전 회차와 인접 청크를 읽기 전용 신원·시점 문맥으로 제공하고, 지칭어 주체는 구체 이름을 이미 출력했더라도 재검증한다.
3. 같은 분석 안의 짧은 이름과 긴 이름이 별도 인물로 생성되면 이후 매칭이 모호해졌다. 저장 전에 신규 이름의 동일인 여부를 회차 원문 근거로 정리하되 값·근거·원본 청크·순서를 보존한다. 이름쌍을 동일인·별개 인물·판단 보류로 구분하고, 동일인/별개 판단은 실제 원문 인용으로 검증한다. 판단 보류인 신규 후보는 미상으로 남겨 검토할 수 있으며 후보 자체를 삭제하지 않는다. 기존 인물을 보호하고 불확실한 연결은 강제하지 않는다.
4. STATUS 값만으로 중복 제거하면 종료→재발→종료의 마지막 관찰이 사라질 수 있었다. STATUS는 청크·정확한 근거·관찰 kind까지 같을 때 합친다. 같은 값과 근거의 START/CHANGE는 각각 보존하고, 기존 kind 없는 active=false와 새 END는 같은 종료 phase로 정규화해 정확한 중복만 제거한다. producer group 번호 자체는 중복 제거 키에 넣지 않으며 외부 저장 필드는 추가하지 않는다.
5. 치료 시작과 회복 결과를 함께 인용한 후보는 맨 앞 근거로 정렬하면 중간 악화보다 앞서 적용될 수 있었다. Java STATUS 정렬은 마지막 유효 근거 위치를 사용한다. 최종 독립 검수에서 저장 mapper의 snake_case를 정렬기가 읽지 못하는 계약 누락도 발견해, 실제 저장된 start_offset과 API startOffset을 모두 해석하도록 수정했다.
6. 기존 공백 포함 STATUS key를 새 key 정규식으로 거절하면 비교가 반복 실패했다. 현재 P/Q에 실제 있는 key는 정확히 재사용할 수 있도록 Java·Python 규칙을 맞췄다.
7. 의역된 STATUS 인용이 null offset으로 저장되던 경계를 차단했지만 제한 재시도만으로는 반복 오류를 해결하지 못했다. 현재 청크를 원문 단위와 E 참조로 제공하고 모델은 참조만 선택하도록 계약을 변경했다. 코드가 정확한 원문과 위치를 연결하므로 이전 화 인용·단어 추가·반복 문장의 위치 혼동을 차단한다. 단위는 비어 있지 않은 줄 안의 문장 경계로 나누며, 동일 문장 안의 여러 변화는 같은 단위를 공유할 수 있다.
8. 평가기의 기존 확정 정책은 REVIEW_REQUIRED 한 건 때문에 인물 전체를 보류했다. 실제 프론트 기본값은 해당 후보를 HISTORY_ONLY로 전체 그룹 확정하는 것이므로 v3에서 동일하게 맞췄다. 이는 제품 판단을 수정한 것이 아니라 평가 경로 차이를 수정한 것이다.
9. 반복 검증에서 STRING 프로필을 배열로 MERGE하는 비교 응답이 Python 검증을 통과하고 Java에서 거절됐다. 단건·배치 공통 경계에서 Java의 제안 타입·값 제약을 검증하고, 잘못된 값은 안전한 타입 피드백으로 재시도하게 했다. 의미나 값을 강제 변환하지 않는다.
10. 과거의 병약함과 현재의 다른 신체를 대비하는 문장이 같은 청크에 있어도 과거 상태만 현재 활성으로 추출한 실행이 있었다. 같은 화자의 기억과 현재 신체의 연속성을 따로 확인하고, 시점을 결정하는 대비 인용까지 보존하도록 STATUS 규칙을 보완했다. 힘이 강해졌다는 이유만으로 잠재 질병을 해소하는 추론은 금지한다.
11. 중복 설정을 제외하는 올바른 첫 비교 응답도 고정 source key 대신 기존 snapshot key를 썼다는 이유로 거절됐다. 상태를 바꾸지 않는 EXCLUDE/HISTORY_ONLY/REVIEW_REQUIRED의 고정 key는 코드가 입력에 묶는다. 연산·target·제거 목록·값·시점 검증은 그대로 적용하며, 잘못된 다른 slot UPDATE는 계속 거절한다. 기록된 첫 실패 응답의 재생이 1호출로 통과했다.

12. 조건부 미래 위험의 목록만 근거로 남기고 조건절을 버려 현재 노출 상태로 오판한 실행이 있었다. STATUS 추출과 배치 비교에 조건·가정·가능성·부정의 발생 여부 판단을 명시했다. 가정 이력에는 조건과 비현재 요약을 보존하고 active를 생략하며, 미발생을 종료로 오해하는 false로 바꾸지 않는다.

13. 같은 ID로 MATCHED된 후보도 entity_name 표기가 달라 검토 그룹이 갈리고, 한 그룹 확정 후 다른 그룹의 비교가 무효화됐다. 저장 경계에서 해당 ID의 대표 이름으로 entity_name만 맞춘다. 원본 추출 payload와 근거·값은 보존한다.
14. 일반 종족·직책 호칭도 문자열 모양만으로 구체 이름 취급되어 새 인물로 등록되는 경로가 있었다. 미등록 SETTING 주체도 문맥 검증을 거치고, 기존 인물에 유일 MATCHED되는 구체 이름만 우회한다. 특정 종족명 사전을 추가하지 않는다.
15. 첫 비교가 회복 근거를 보고도 관련된 이전 상태 일부를 놓쳤다. 전체 STATUS batch의 비교·fallback 후 남은 상태를 한 번씩 검수하고, 기존 현재 관찰의 근거로 끝난 상태만 해당 관찰의 제거 집합에 추가한다. 전체 projector를 다시 실행해 과거·미래 참조와 Q 의존성을 검증하며, 원문이나 후보를 새로 만들지 않는다. 이 검수는 기존 후보에 없는 원문 관찰을 복구하지 않는다.
