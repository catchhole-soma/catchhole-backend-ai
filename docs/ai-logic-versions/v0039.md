# v0039 — BASELINE으로 요청한 항목을 전체 행 대신 값 이력 확장 행으로 판정에 전달

2026-10-31 · 적용: 작업 브랜치 `fix/gh-349-judge-baseline-projection` · [Java #349](https://github.com/catchhole-soma/catchhole-backend-java/issues/349) 후속 · 이전 v0038

## 무엇을 바꿨나

- v0038은 COVERAGE·JUDGE에 압축 행을 보내되 모델이 BASELINE으로 요청한 항목만 "전체 행"으로 돌려줬다. 운영 첫 완주 시도(31화, 질문 65개)에서 첫 판정 8건 중 7건이 FOLLOW_UP으로 BASELINE 조회를 요청했고, 이력 209 KB를 가진 인물 항목을 요청한 질문의 두 번째 JUDGE가 입력 80,000토큰을 넘겨 `REQUIRED_CONTEXT_TOO_LARGE`로 Job이 멈췄다(판정 18회·정산 약 108만 토큰 뒤).
- 이제 BASELINE으로 요청한 항목은 `expanded_setting_row`로 보낸다: 압축 행 + `state.historyFacts`를 factType·factKey·factValue·operation·effectiveFromEpisodeNo·temporalScope만 남긴 목록(최신 300개, 초과분은 `historyTruncated` 개수). 슬롯 출처·근거 인용·provenance·identityEvidence는 여전히 보내지 않는다. 조회(`BASELINE`/`HISTORY` receipt)와 Worker 검증·게시 bundle은 바꾸지 않았다.
- system prompt의 한 문장을 "전체 행"에서 "값 이력을 더한 확장 행(근거·출처 없음, 오래된 이력 생략 가능)"으로 고쳤다.

## 평가

| 항목 | 결과 |
| --- | --- |
| 확장 행 투영 | 이력 2건·슬롯 provenance가 있는 합성 인물: 이력은 6개 필드만, provenance 없음, `max_history=1`이면 최신 1건과 `historyTruncated=1`, 입력 원본 불변 |
| JUDGE 2회차 입력 | BASELINE 요청 뒤 두 번째 JUDGE settings가 전체 정본 행이 아니고 historyFacts(값)만 포함 |
| 회귀 | `tests/test_validation_projection.py`, `tests/test_setting_validation_service.py`, `tests/test_validation_checkpoint.py` 통과(가짜 모델) |
| 실제 모델 재실행 | 운영 31화 재시도로 확인 예정(리뷰어) |

## 남은 문제

- 판정이 질문당 약 2회(첫 판정 FOLLOW_UP → 조회 → 재판정)라 회차당 토큰·시간이 크다. 질문 수·판정 묶음·조회 선실행·prompt cache는 [Java #354](https://github.com/catchhole-soma/catchhole-backend-java/issues/354)에서 다룬다.
- 이력 300개 상한은 보수적 안전장치다. 더 긴 이력이 판정에 필요한 사례가 나오면 HISTORY 조회로 범위를 지정하는 쪽을 검토한다.
