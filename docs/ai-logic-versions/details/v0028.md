## 변경 이유와 실행 경계

서버가 분석 상태를 재구성하는 동안 정상 응답이 기존 30초 읽기 한도를 넘으면,
Worker는 응답 수신 전 transport 오류를 받고 진행 중 Job을 실패 처리할 수 있다.
공통 SQL/상태 재구성 최적화는 #294 Backend 변경에서 다루며, 이 AI 변경은
정상적인 분석 API 응답을 기다릴 여유를 별도로 설정한다.

`SPRING_WORKER_READ_TIMEOUT_SECONDS`는 유한 양수이며 기본값은 120초다.
최초 claim, 후보 게시·비교 claim, 상세 문맥, progress, complete, fail에 요청별 적용한다.
HTTPX client 자체의 timeout은 바꾸지 않으므로 같은 client의 동시 heartbeat·token 원장은
기존 read 30초를 유지한다. connect/write/pool도 각각 기존 30초다.
주입 client는 자체 connect/write/pool 및 제어 요청의 한도를 보존하고 분석 read만 바꾼다.
세 Worker Compose 서비스에 공통 환경변수로 전달한다.

read timeout은 응답 헤더/다음 바이트를 기다리는 한 번의 읽기 한도다.
전체 HTTP 요청이나 Job에 대한 절대 120초 deadline이 아니다.
heartbeat의 60초 주기, 최대 3회 시도, 2/4초 재시도 간격과 최종 실패 시 소유 작업 취소를 유지한다.
같은 Job 잠금으로 세 heartbeat가 각각 read 30초를 소진하면 첫 시도부터 약 96초 뒤
취소할 수 있다(연결 등 다른 I/O 대기는 별도). 따라서 분석 read 한도에 도달하기 전에도 끝날 수 있다.
lease 검증/회수, 기존 typed transport 오류·진단, token 원장 멱등 재시도는 그대로다.
일반 분석 POST 자동 재전송을 추가하지 않아, 서버 처리 여부가 불명확한 요청을 중복 발행하지 않는다.

## 검증 — 2026-10-29 gh294-ai-timeout

담당: #294 AI 구현 작업자. Python 3.12.13 / HTTPX 0.28.1.
기존 검증 venv의 의존성만 읽어 사용했으며 제품 import는 gh294 checkout으로 확인했다.
환경 설치·원래 checkout 수정 없이 아래 명령을 gh294에서 실행했다.

| 검증 | 명령·조건 | 결과 |
| --- | --- | --- |
| 집중 회귀 | `python -m pytest -q tests/test_spring_worker_timeouts.py tests/test_spring_worker_client.py tests/test_config.py tests/test_lease_heartbeat.py tests/test_spring_http_tracing.py` | 116 passed, 3.13초 |
| 전체 회귀 | `python -m pytest -q` | 4,628 passed / 140 skipped / 기존 Starlette 경고 1, 30.52초 |
| 정적 검사 | `python -m ruff check app/clients/spring_worker_client.py app/core/config.py tests/test_spring_worker_timeouts.py` | 통과 |
| diff 공백 검사 | `git diff --check` | 통과 |
| Compose 렌더 | 합성 env의 기본값/180.5 설정으로 `docker compose ... config --format json` | 세 서비스 모두 각각 120/180.5 전달. daemon·배포 호출 없음 |

신규 15개 회귀에는 실제 loopback TCP HTTP 검증 3개가 포함된다.

1. 기존 30→새 120초를 0.1→0.4초로 축척하고 0.2초 뒤 응답한다.
   이전 한도에서는 `ReadTimeout` 원인을 가진 기존 typed transport 오류,
   새 한도에서는 claim 정상 응답을 받는다. 각각 POST 1회로 재전송이 없다.
2. 느린 claim 응답 대기 중 독립 heartbeat가 성공하고 claim도 완료된다.
3. heartbeat read 실패 3회가 소유 claim task를 취소한다. 분석 read 한도를 늘려도
   lease 보호가 우회되지 않으며 claim POST는 1회다.

설정의 0·음수·NaN·무한대 거절, from_settings 전달, 연결/쓰기/pool 유지,
heartbeat·token 원장 분리도 함께 확인했다. 기존 오류·재시도·tracing 회귀를 재사용했다.
최초 집중 실행의 테스트 fixture가 원장 outcome을 지원하지 않는 `FAILED`로 넣어 1개 실패했다.
fixture를 기존 계약의 `FAILURE`로 바로잡은 뒤 위 집중/전체 결과를 얻었다. 제품 계약 변경은 없다.

## 미측정과 다음 확인

모델·추론·prompt/schema·토큰 예산·청킹·provider 재시도 설정은 바꾸지 않았다.
이번 검증은 합성 HTTP/자동 회귀이며 provider·judge 호출은 없다.
캐릭터/세계관 P/R/F1·값/결정 정확도·Gold·토큰/비용·운영 실패율·실제 사고 재분석은 미측정이다.
전송 대기 변경이라 실제 모델 품질 평가를 수행하지 않았고, 자동 회귀 통과를 의미 품질로 환산하지 않는다.
운영 적용은 별도 승인 흐름에서 수행한다. #294 담당자가 Backend 최적화와 함께
claim/context/complete 시간, SQL/상태 재구성 비용, heartbeat/timeout 실패를 관찰해야 한다.
read 여유가 서버의 장시간 잠금이나 성능 병목을 해결했다는 주장은 하지 않는다.

원문·Gold·개별 예측·인증/lease 비밀값을 기록에 복사하지 않았다.
