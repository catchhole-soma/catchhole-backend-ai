서버가 60초 lease를 발급한 뒤 복구 문맥을 준비하는 동안 시간이 흐르지만,
전용 Worker는 claim 응답 후에도 20초를 기다려 첫 heartbeat를 보냈다.
준비·응답 시간이 40초 이상이면 첫 갱신 전에 만료될 수 있다.
운영에서 첫 사용량이 UNKNOWN으로 남고 같은 복구 Job이 두 번 claim된 기록을 확인했다.
실제 준비 지연을 직접 측정한 것은 아니므로 해당 경합이 유일한 원인이었다고 단정하지 않는다.

관계 Worker만 `renew_now()`의 기존 전송 오류 재시도(최대3회, 기본2/4초)를 기다린다.
성공한 뒤 기존20초 주기와 pipeline을 시작한다. 초기 실패·취소에서는 원문 읽기·provider·
예약을 시작하지 않는다. 공용 heartbeat의 기존 진입·주기 동작과 캐릭터·세계관 실행은 유지한다.
Java의 준비 완료 후 동일 lease 갱신과 함께 배포한다. 모델·프롬프트·관측 검증·회차당
복구1회·lease 회수 최대3회는 바꾸지 않는다.
