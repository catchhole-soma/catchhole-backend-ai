운영의 기존 원고 한 개가 365,127 code points / 809,697 UTF-8 bytes였다.
현재 출처 검사와 실제 본문의 SHA-256 비교는 일치했지만, 250,000자 검사도 `SourceChanged`를 던져 백필이 중단됐다.
운영 원문·key·hash·회원/작품 식별값은 기록하지 않는다. 이 진단은 수정 전 운영 읽기 확인이며 새 코드의 운영 검증이 아니다.

`app/retrieval/service.py`는 기존 저장소 다운로드 상한 2,000,000 bytes를 유지하고,
별도 250,000자 검사를 제거한다. 대체 저장소를 포함해 실제 UTF-8 byte 수를 재검증한다.
크기 초과는 기존 `SOURCE_UNREADABLE`, 실제 본문 hash/출처 불일치는 `SOURCE_CHANGED`로 구분한다.
Java 검색 인용 검증도 같은 byte 경계를 적용해야 한다. 신규 업로드·수정 정책은 유지한다.
원문은 자르거나 정규화하지 않으며 code point offset·hash·800/100토큰 청크·정책/모델/버전을 유지한다.
기존 벡터·진행 위치·누적 예산을 재사용하고, 사용자 토큰을 차감하지 않는 운영 원장 계약도 유지한다.

## 리뷰 후 성능 검증 — 2026-10-16-boundary-bisect

코드 `59260548d3c125bd91fdadc528fc7e0e5fea7112`는 정렬된 문장 경계에서 마지막 `start < b <= end`,
첫 `overlap <= b < end`를 이진 탐색한다. 문장 선택·800/100토큰·offset/hash·정책 문자열은 유지한다.
기준 `3b8e5747e7df5fc734fe63828f98b2afc9e60fd7`의 기존 출력을 고정한 3개 회귀가 통과했다.
최종 전체 pytest는 **3,991 passed / 132 skipped / 기존 warning 1**, 16.85초다.
변경된 chunking 모듈·테스트의 Ruff check/format과 `git diff --check`도 통과했다.

별도 프로세스에서 합성 자연문(54,250 bytes, 30청크)과 경계 밀집 입력(200,000 bytes, 286청크)의
모든 slice 필드(index/start/end/text/tokens/hash)가 기존 구현과 일치했다.
자연문 시간은 0.161→0.162초, 200KB는 3.975→3.650초였다.
2MB/백만 경계는 기존 구현이 45초 제한으로 종료됐고 수정 구현은 37.234초/2,857청크로 완료했다.
최대 입력의 기존 출력 비교는 시간 제한으로 미검증이며, 이 수치를 운영 시간 보장으로 해석하지 않는다.
원문·provider·judge API를 사용하지 않은 로컬 합성 검증이다.
근거: `.codex-artifacts/gh258-review-20261016/chunking_bisect_benchmark.json`,
`legacy-source-ai-review-full-tests.log`. 운영 백필·실제 답변 평가는 별도다.

## 남은 작업과 배포 조건

실제 질문 품질·recall·지연/비용은 변경하지 않았다고 가정해 점수로 대체하지 않고 미측정으로 남긴다.
담당자는 배포 후 기존 대용량 원고의 백필 진행과 인용 열기를 확인하고, 품질 평가는 #242에서 수행한다.
Java 수정 배포 → AI 수정 배포 → 실제 이미지 확인 → 기존 campaign의 보고·불확실 상태 확인 → 명시적 resume 순서다.
`BLOCKED`는 코드 배포만으로 해제되지 않는다. 최초 공개가 먼저 실패하면 준비 완료 뒤 최신 AI 배포를 재실행한다.
2,000,000 bytes도 넘는 원고는 자동 제외하지 않으며 원문 자르기·예산 초기화·공개 게이트 우회는 하지 않는다.
Java 저장소는 전체 다운로드 뒤 검사한다는 기존 메모리/전송 제한을 공통 계약에 계속 명시한다.

추가 독립 검토에서 정상 1,400청크의 실행은 1,000개 처리 후 다음 주기에 나머지만 이어지는 것을 합성 확인했다.
다만 사용량이 확인된 일시 실패를 각 batch에서 재시도하면 단일 실행의 1,000,000토큰 한도가
캠페인 전체 `BUDGET_EXHAUSTED`로 저장되는 기존 상태 구분 한계가 재현됐다.
큰 원문 자체의 정상 경로와 구분하며, 누적 예산이 남아도 명시적 resume가 필요한 이 한계는 #247 후속으로 남긴다.
이번 수정에서 예산/상태 처리는 바꾸지 않으며 이 합성 검토를 실제 운영 비용 측정으로 사용하지 않는다.
