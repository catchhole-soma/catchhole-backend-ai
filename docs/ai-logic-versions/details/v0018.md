## 실행과 복구

- 같은 회차 Job/청크의 두 추출을 `asyncio.gather(return_exceptions=True)`로 시작한다. 다음 청크는 두 추출과 캐릭터 식별/시점 문맥 처리가 끝난 뒤 진행한다. 설정집 실행은 기존 순차 방식이다.
- Job 로컬 dict에 세계관 결과를 보관하고, 기존 캐릭터 저장/비교 이후 세계관 게시 단계에서 사용한다. 공유 Worker 필드나 DB 스키마를 추가하지 않는다.
- Job 슬롯·프로세스별 생성 요청 세마포어·metered client의 토큰 예약/정산·heartbeat/lease를 유지한다. 동시에 두 요청을 시작해도 기존 요청 슬롯이 하나면 하나는 대기한다.
- 한쪽 실패는 다른 요청도 종료한 뒤 기존 typed failure로 보고한다. Job 취소는 두 요청을 취소하며 lease 복구에 맡긴다.
- 재시작 시 저장된 청크와 checkpoint만 신뢰한다. 캐릭터 후보 저장 이후에는 세계관만, 세계관 게시 이후에는 추출 없이 다음 단계를 실행한다. 응답 후 게시 전 종료된 세계관은 다시 호출될 수 있다. 외부 API의 exactly-once를 보장하지 않는다.

## 별도 큐를 추가하지 않은 이유

현재 Spring의 DB `AnalysisJob`이 영속 작업 목록 역할을 한다. pending Job claim, lease/heartbeat, checkpoint, 만료 작업 재대기가 이미 있다. 병렬 요청은 이 Job 하나의 내부 실행이며 별도의 독립 작업으로 분리하지 않는다. 프로세스 종료 후 작업을 복구할 수 있는 것과, 응답을 받은 직후의 결과까지 보존하는 것은 구분한다. 세계관 응답 재요청을 줄이려면 검증된 추출 결과를 원문/input hash/lease와 함께 영구 저장하는 변경이 직접적이며, 메시지 큐 추가만으로 provider 응답 수신과 DB 저장 사이의 공백이 없어지지는 않는다.

읽기 확인한 Java 기준 `28cfd63690e24b6763db5c5ec34502b6819acef7`의 `AnalysisJobWorkerServiceImpl`은 claim 시 만료 작업을 회수한다. lease는 5분이며 claim 횟수 3회에 도달한 반복 만료는 실패로 기록한다. 명시적으로 보고된 추출 실패는 기존 실패 정책을 따르며 무조건 자동 재대기되는 것이 아니다. 이번 테스트는 Python 취소·저장 경계의 합성 회귀이며 실제 운영 프로세스 강제 종료/DB 장애 주입 검증은 아니다.

- 최초 전체 실행: 4,054 통과/134 skip/3 실패. 1개는 의도된 세계관 prompt 요청 hash, 2개는 sandbox loopback bind 금지였다. 과거 golden을 보존한 override를 추가하고 로컬 포트 허용 후 4,057 통과/134 skip/경고 1개를 확인했다.
