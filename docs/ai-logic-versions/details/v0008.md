## 남은 일과 운영 경계

- #240 담당이 같은 원문/모델/버전/작품 범위를 모든 검색·이웃·인용 경로에 적용하고 실제 질문에 연결한다.
- 작은 유료 임베딩 표본에 대한 검색/근거 정확도 평가는 별도 실행 범위를 정한 뒤 #240에서 수행한다.
  800/100은 초기 정책이며 최적값을 입증하지 않았다. 담당: 챗봇/원문 검색 구현자.
- 신규 분석은 검색 청크 준비까지만 연결한다. 새 원고의 벡터도 운영 실행기를 소비 경로로 사용한다.
  상시 실행 스케줄/예산과 실제 400여 회차 백필은 운영 배포 때 정한다.
- 검색 실행기는 한 작품/한 예산으로 제한된 one-shot이다. 기존 27개 DB 연결 예산 때문에
  운영 백필 시 분석 Worker 1개를 drain해 2개 연결을 확보한다. 실제 drain/배포는 수행하지 않았다.
- 강제 종료 시 완료 벡터는 재사용하지만 provider 응답과 DB 저장 사이 종료의 중복 외부 호출은 가능하다.
  실측 보고를 잃으면 UNKNOWN이며 0으로 정산하지 않는다.
- RDB 질문 분류·동적 항목/scope·전체 이력 누락·사용자 답변 표현·상한 측정은 [Java #247](https://github.com/catchhole-soma/catchhole-backend-java/issues/247)에 후속 한계로 누적 관리한다. 이 PR은 해당 QA 로직을 변경하지 않는다.
