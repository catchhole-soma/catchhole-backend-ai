## 재현

테스트 전용 localhost DB를 별도로 생성한다. 운영 DATABASE_URL이나 로컬 .env를 사용하지 않는다.

```bash
docker run -d --name catchhole-gh239-test -e POSTGRES_USER=gh239 -e POSTGRES_PASSWORD=gh239-test-only -e POSTGRES_DB=gh239_test -p 127.0.0.1:35439:5432 pgvector/pgvector:0.8.2-pg16
GH239_TEST_DATABASE_URL=postgresql+psycopg://gh239:gh239-test-only@127.0.0.1:35439/gh239_test GH239_JAVA_CHECKOUT=/absolute/path/catchhole-backend-java .venv/bin/python -m pytest -q
```

Java checkout에서는 Java 21, Docker/Testcontainers 연결을 설정한 뒤:

```bash
GH237_AI_CHECKOUT=/absolute/path/catchhole-backend-ai GH238_AI_CHECKOUT=/absolute/path/catchhole-backend-ai ./gradlew test bootJar
```

GH239 Python DB 검증은 매번 새 schema에 Java V1~V76 SQL을 적용하고 정리한다.
Java는 실제 Flyway 자체를 검증한다. 로컬 실행 로그는 workspace의
`.codex-artifacts/gh239/{python-full,java-full,java-focused}.log`에 보관했다.
로그는 부가 자료이고 복원 가능한 근거는 위 SHA/테스트/명령이다.

## 남은 일과 운영 경계

- #240 담당이 같은 원문/모델/버전/작품 범위를 모든 검색·이웃·인용 경로에 적용하고 실제 질문에 연결한다.
- 작은 유료 임베딩 표본에 대한 검색/근거 정확도 평가는 별도 실행 범위를 정한 뒤 #240에서 수행한다.
  800/100은 초기 정책이며 최적값을 입증하지 않았다. 담당: 챗봇/원문 검색 구현자.
- 신규 분석은 검색 청크 준비까지만 연결한다. 새 원고의 벡터도 운영 실행기를 소비 경로로 사용한다.
  상시 실행 스케줄/예산과 실제 400여 회차 백필은 운영 배포 때 정한다.
- 검색 실행기는 한 작품/한 예산으로 제한된 one-shot이다. 기존 27개 DB 연결 예산 때문에
  운영 백필 시 분석 Worker 1개를 drain해 2개 연결을 확보한다. 실제 drain/배포는 수행하지 않았다.
- 강제 종료 시 완료 벡터는 재사용하지만 provider 응답과 DB 저장 사이 종료의 중복 외부 호출은 가능하다.
  실측 보고를 잃으면 UNKNOWN이며 0으로 정산하지 않는다.
