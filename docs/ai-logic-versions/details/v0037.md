## 바뀐 동작

1. **VECTOR 제안 조건.** 이전(v0032 GH331)에는 frozen RAG가 주입되면 항상 KEYWORD·VECTOR를 제안했다. 운영 색인은 일부 회차가 빠질 수 있어(작품 426·회차 845 중 `retrieval_sources` 804), 모델이 VECTOR를 고르면 `search()`의 `VECTOR_NOT_READY`나 corpus의 `VECTOR_INDEX_PARTIAL`로 설정 분기 전체가 끝났다. 이제 `SettingValidationService._search_operations()`가 `inspect()` 시작 때(구간·PLANNER 전) 다음 순서로 정한다.
   - 회차 출처가 없으면 기존대로 KEYWORD·VECTOR(설정집 raw fallback).
   - frozen RAG가 없으면 기존대로 KEYWORD만.
   - 같은 Job의 이전 시도가 VECTOR 계획·의무·receipt를 저장했으면 KEYWORD·VECTOR 유지(`resumed=True`, 아래 3).
   - 그 밖에는 `FrozenRetrievalSearchService.readiness(frozen)`로 `search()`와 같은 `FrozenSearchScope`의 readiness를 한 번 읽어, `vector_chunks>0`·`vector_ready_sources == source_count`·query embedding client 있음(공용 `vector_ready`)과 `source_count == 회차 출처 수`(corpus의 VECTOR 성공 조건)를 모두 만족할 때만 KEYWORD·VECTOR, 아니면 KEYWORD만.
2. **진단.** `normalizations.VECTOR_OFFERED`=1/0, INFO `vector search offered=<bool> sources=<n> ready=<m> chunks=<c> episodes=<e> embedding=<bool> job=<jobId>`. readiness 읽기 실패(DB 오류·timeout)는 Job을 실패시키지 않고 KEYWORD만 제안하며 WARNING `vector search readiness unavailable error=<예외 종류> job=<jobId>; offering KEYWORD only`만 남긴다(메시지·URL 없음). 읽기는 Job 남은 seconds 예산 안에서 하며 lookup 예산은 쓰지 않는다.
3. **재개 보존.** 제안 목록은 저장된 PLANNER/COVERAGE 단계 재검증에도 쓰인다. 첫 시도에서 VECTOR가 성공한 뒤 색인이 재구축 중이면 재개가 `VECTOR_NOT_READY`로 막혀, 검수 실행 계약의 "이미 성공한 조회의 JUDGE-only 재개는 live index 재구축 때문에 막지 않는다"를 어기게 된다. 그래서 `ValidationCheckpoint.planned_operations()`(저장 단계·check bundle·runtime의 `operation` 수집)에 VECTOR가 있으면 readiness를 읽지 않고 유지한다. 아직 실행하지 않은 VECTOR 의무는 조회 직전 검사로 기존과 같게 실패한다.
4. **마지막 방어선 유지.** `search()`는 조회마다 readiness를 다시 읽어 `vector_ready`가 거짓이면 `VECTOR_NOT_READY`, corpus는 부분 색인이면 `VECTOR_INDEX_PARTIAL`을 그대로 낸다.
5. **embedding 설정.** `metered_embedding`은 claim에 `models.QUERY_EMBEDDING`과 `budgets.roles.QUERY_EMBEDDING`이 모두 없거나 null이면 None(키워드만)을 돌려준다. 있는데 model/version/dimensions가 index와 다르거나 cap이 0이거나 한쪽만 있으면 `EMBEDDING_CONFIGURATION_INVALID`를 유지한다.
6. **runner·배포.** `--readonly-url-env` 변수가 없거나 비면 INFO `frozen retrieval disabled: <NAME> is empty`, session 없는 `--query-embedding`은 INFO `query embedding disabled: no read-only retrieval sessions`로 계속 실행한다(--once 동일). URL이 있으면 읽기 전용 pool은 `--concurrency`개·overflow 0이다. Compose는 세 플래그를 고정으로 넘기고 URL 기본값은 빈 값이다. `manage-ai-runtime.py`는 URL이 있을 때만 챗봇 reader URL·embedding version 일치와 `검수 프로세스 × AI_WORKER_CONCURRENCY` 연결 예산을 검사한다.

판정·사유·영향 등급·질문 병합·예산·모델·추론 강도·prompt·Backend 계약은 바꾸지 않았다. 의미 검색이 켜진 Job에서는 모델이 VECTOR를 고를 수 있어 query embedding 호출과 사용량이 늘 수 있다(서버 QUERY_EMBEDDING cap 안).

## 미측정

- 실제 모델·운영 DB 재실행은 하지 않았다(리뷰어 담당). 확인할 것: 운영 색인이 완전한 작품에서 `vector search offered=True`와 VECTOR 조회 성공, 부분 색인 작품에서 `offered=False`·키워드만으로 COMPLETED, 의미 검색이 판정 품질·사용량·지연에 주는 영향.
- 실제 PostgreSQL에서 readiness 질의 시간과 Job 슬롯당 연결 1개 가정(조회는 Job 안에서 순차)은 합성 테스트로만 확인했다.
