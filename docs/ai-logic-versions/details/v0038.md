## 근거(운영 관측, 2026-10-31, 변경 전 v0036/v0037 코드)

- 30회차 작품의 첫 grid v2 실행: `PLANNER:TSEG1`, `SUBJECT_RESOLUTION:TSEG1` 성공(모델 호출 2회, mentions 3개). 다음 `COVERAGE:TSEG1`은 count 결과가 `setting.input-tokens`(80,000)를 넘어 호출 전에 `REQUIRED_CONTEXT_TOO_LARGE`.
- 4구간 기계 매칭 주체 21/22/16/16(매칭된 이름 1~7글자, 여러 개가 1~2글자). 기준 773항목·276주체. TSEG1 관련 항목 179개 → raw JSON 795 KB(평균 4.4 KB/항목).
- 가장 큰 인물 항목 362 KB: `state.slots` 149 KB(78슬롯, 슬롯마다 factKey/factType/factValue/valueJson 외에 `provenance` 약 565 B·`supportingSources` 약 861 B), `state.historyFacts` 209 KB. 그 밖의 state 키 `name`, `aliases`, `absences`, `provenance`, `protectedSlots`, `snapshotVersion`, `identityEvidence`, `currentNarrativeTime`, `currentSupportingEvidenceVersion`. 서버 투영 `toValidationModelState`는 id/hash/S3 키와 일부 비공개 키만 뺀다.
- 원인은 호출 수가 아니라 항목 크기이며, 같은 큰 행이 JUDGE 호출마다 다시 들어간다.

## 바뀐 동작

1. **압축 투영(`compact_setting_row`).** 행은 `entry_ref`, `subject_ref`, `domain`, `name`, `aliases`, `state`, 행에 있으면 `author_correction`(실행 Job은 항상 null, 호출형은 기존 값 그대로). `compact_state` 규칙:
   - `slots`(슬롯 key → 객체): 슬롯마다 `factKey`, `factType`, `factValue`와 스칼라인 `temporalScope`, `effectiveFromEpisodeNo`만. 슬롯의 `valueJson`, `provenance`(그 안의 `source_ref` 포함), `supportingSources`는 뺀다.
   - 그대로 둠: 스칼라(문자열·숫자·불리언·null), 스칼라 목록(예: `aliases`), 세계관 `propertiesJson`(작가가 정한 설정명이 key라 내용 그대로), `currentNarrativeTime`·`narrativeTime`·`absences`·`protectedSlots`·`protectedPaths`(안의 근거 키만 제거).
   - 뺌: `historyFacts`, `supportingSources`, `supportingSource`, `provenance`, `provenanceByPath`, `identityEvidence`, `removedSnapshotEntries`, `valueJson`, `evidenceSpans`, `comparison`, `explicitAuthorCorrections`, `snapshotVersion`, `currentSupportingEvidenceVersion`, `version`과 위에 없는 모든 중첩 목록·객체.
   - 도메인별: 인물(`characters`)은 `name`·`aliases`·`protectedSlots`·`currentNarrativeTime`(supportingSource 제거)·`absences`·압축 `slots`. 세계관(`worldSettings`)은 `category`·`subjectName`·`normalizedSubjectName`·`propertiesJson`·`protectedPaths`·`latestSourceEpisodeNo`(뺌: `version`·`provenanceByPath`·`provenance`). 세계관 이력(`worldHistory`)은 `category`·`subjectName`·`scopeName`·`settingName`·`value`·`operation`·`historyOnly`·`effectiveFromEpisodeNo`·`temporalScope`·`sourceAvailability`·`narrativeTime`·출처 스칼라(`sourceKind`·`sourceEpisodeNo`·`source_ref` 등)(뺌: `evidenceSpans`·`comparison`).
   - 순수 함수이며 원본 행을 바꾸지 않는다.
2. **적용 위치.** COVERAGE 호출의 `settings`(관련 항목)와 JUDGE 호출의 `settings`(질문 주체 항목 + BASELINE 선택). BOOK_COVERAGE는 원래 `settings: []`, PLANNER·SUBJECT_RESOLUTION은 settings가 없다. 고정 항목 읽기, Worker 검증(`_validate_decision`의 사실·author_correction), receipt, checkpoint, `evidence_bundles`는 전체 행이다. 게시 `evidence_bundle`의 `settings`는 Backend `ValidationDecisionValidator`가 서버 정본 행과 `same()`으로 비교하므로 바꿀 수 없고, `input_digest`도 전체 bundle로 계산한다(모델은 같은 digest를 받는다).
3. **BASELINE 요청 항목은 전체 행.** 질문의 성공 receipt 가운데 `operation=BASELINE` 의도의 `evidence_refs`(PLANNER/COVERAGE 조회 의무나 JUDGE FOLLOW_UP으로 모델이 요청한 B 참조)에 든 항목은 다음 JUDGE 입력에 전체 행으로 보낸다. Worker가 자동으로 붙이는 `Qn-BASELINE` receipt는 `evidence_refs`가 비어 있어 해당하지 않는다. 재개 때는 저장 receipt에서 같은 집합을 다시 계산한다.
4. **1글자 규칙.** `mechanical_subject_refs`는 `len(value) >= MECHANICAL_NAME_MIN_CODE_POINTS`(2, Python code point)인 name·alias만 쓴다. 😀처럼 UTF-16 두 단위여도 code point 하나면 제외한다. `subject_catalogue`는 그대로라 SUBJECT_RESOLUTION이 문맥으로 해소할 수 있다.
5. **grid v3.** `grid_segment_subjects`는 정수 `gridVersion` 2·3(`SUPPORTED_SETTING_GRID_VERSIONS`)을 받는다. v4·문자열 "3"·v1·없음은 `GRID_VERSION_UNSUPPORTED`. grid v3 = v2 + 1글자 제외(모양 동일). 공통 fixture의 SETTING `gridVersion` 다섯 곳(gridCases `expectedSetting` 4곳, `progressiveSourceGrid` 1곳)을 3으로 바꿨고 TYPO grid 1은 그대로다. 이 브랜치의 사본은 같은 시점 Backend 작업 사본과 byte 단위로 같았다(`cmp`). fixture 사례에는 1글자 이름이 없어 `segmentSubjects`는 바뀌지 않는다.
6. **COVERAGE 안전장치.** 관련 항목이 `MAX_COVERAGE_SETTINGS`(400)를 넘으면 카탈로그 순서 앞 400개만 압축해 보내고 `rule_refs`·schema enum도 그 400개다. 모델 응답을 정규화한 뒤 나머지 entry_ref마다 `{"status": "NOT_APPLICABLE", "reason": "입력 상한으로 모델 점검에서 제외됨"}`를 rules 끝에 더하므로 저장 rules는 관련 항목 전체다(Worker `validate_batch`, Backend의 rules 집합·CHECKED/NOT_APPLICABLE·사유 검사와 같은 조건). 이미 rules에 있는 ref는 더하지 않으므로 재개한 batch는 그대로다. WARNING `coverage settings truncated total=<n> kept=400 segment=<TSEGn>`, `normalizations.COVERAGE_SETTINGS_TRUNCATED`에 구간 합계. JUDGE에는 행 수 상한이 없다.

## 미검증·남은 문제

- **실제 모델 재실행: 리뷰어 확인 예정.** 같은 30회차 작품으로 COVERAGE 입력 토큰이 80,000 안에 드는지, 지칭 해소가 1글자 이름 주체를 찾는지, Java↔Python HTTP 계약 테스트(`ValidationExecutionHttpPostgresIntegrationTest`)는 이 브랜치에서 실행하지 않았다.
- 게시 `evidence_bundle`은 전체 정본 행이라 큰 인물(362 KB)을 다루는 질문의 JUDGE 게시는 게시 외피 131,072 UTF-8 byte 상한을 넘을 수 있다(Backend bundle 검증을 바꿔야 해결되며 이 변경 범위 밖).
- JUDGE에는 행 수 상한이 없어, 한 주체의 항목이 매우 많거나 모델이 큰 항목을 BASELINE으로 요청하면 JUDGE가 `REQUIRED_CONTEXT_TOO_LARGE`로 멈출 수 있다.
- 압축 행에는 슬롯의 출처(`provenance.source_ref`·출처 회차)와 이력이 없다. 모델이 BASELINE으로 요청하지 않으면 변화·출처 판단은 검색 근거에 기댄다. 판정 품질 영향은 미측정이다.
- 안전장치로 제외된 항목은 그 구간 COVERAGE가 읽지 않은 것이며 NOT_APPLICABLE은 "해당 없음"이 확인됐다는 뜻이 아니다(사유 문구로 구분).
