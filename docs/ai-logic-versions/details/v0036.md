## 바뀐 동작

1. **주체 카탈로그.** `subject_catalogue(settings)`가 주체당 한 행 `{subject_ref, domain, name, aliases}`를 만든다. domain·name은 그 주체의 첫 항목, aliases는 모든 항목 aliases의 순서 보존·중복 없는 합집합이다. PLANNER·SUBJECT_RESOLUTION·COVERAGE·BOOK_COVERAGE 입력에 같은 목록을 쓴다. 질문 `subject_refs` 검증은 여전히 전체 주체 기준이다. 이전 행별 목록에 있던 `entry_ref`가 빠지므로 PLANNER는 B 참조를 보지 않는다(질문별 BASELINE 영수증은 Worker가 주체 기준으로 계속 붙인다).
2. **기계 매칭.** 실행 Job은 서버 SETTING grid의 `segmentSubjects`만 쓴다. grid는 첫 의미 단계(PLANNER:TSEG1) 게시 때 서버가 만들므로 `ValidationCheckpoint.setting_grid()`가 SETTING grid가 없을 때 한 번 GET checkpoint로 다시 읽는다. `gridVersion`이 정수 2가 아니거나 `segmentSubjects`가 없으면 `GRID_VERSION_UNSUPPORTED`, 행이 구간 순서와 다르거나 알 수 없는/중복 S 참조가 있으면 `INVALID_GRID_CONTRACT`다(failure_stage `SUBJECT_RESOLUTION:TSEGn`). Job 없는 호출형(합성 pytest 포함)은 `mechanical_subject_refs`로 같은 규칙을 계산한다: 비어 있지 않은 name/alias 문자열이 `text[contextStart:contextEnd]`(code point)에 정확한 부분 문자열로 나오면 매칭, 정규화 없음, S 번호 순·중복 없음.
3. **SUBJECT_RESOLUTION.** PLANNER 다음·COVERAGE 전, 구간당 한 번. `stage()` 도우미에 단계 이름과 호출 역할을 분리하는 `role`을 더해 `call_role(..., "RELATED_SELECTION", ...)`으로 부른다(ROLE_OPTIONS·역할 예산·원장 role 불변, prompt의 `role`도 RELATED_SELECTION). 입력은 구간 공통 입력 + `subject_catalogue` + `mechanical_subject_refs`. schema `subject_resolution_schema(subject_refs=보고서 S 목록)`는 보고서당 한 번 만들며 `subject_ref`를 S enum 또는 null로 제한한다(100개 초과는 S pattern, 주체 0개면 null만).
4. **검증.** 서버와 같은 규칙: mention·reason 공백 아님(`SUBJECT_RESOLUTION_BLANK`), mention 중복 없음(`_DUPLICATE_MENTION`), subject_ref는 null 또는 카탈로그 S(`_UNKNOWN_SUBJECT`). 분류 코드는 `SUBJECT_RESOLUTION_INVALID`이고 검증 실패는 저장하지 않는다. 이미 매칭된 주체를 가리키는 mention은 허용하고 무시한다.
5. **호출 생략.** 해소할 주체가 남지 않으면(주체 0개 또는 모든 주체가 이미 매칭) 모델 출력이 관련 주체를 바꿀 수 없으므로 `stage(..., fixed=SubjectResolution(mentions=[]))`로 호출 없이 저장·게시한다. 이전에도 빈 카탈로그는 페이지가 0개라 선정 호출이 0이었다.
6. **COVERAGE.** 관련 주체 U = 매칭 ∪ null이 아닌 subject_ref. `settings`·`rule_refs`는 U의 모든 항목(카탈로그 순서), 비어 있을 수 있다. 검증·schema·clue 처리는 그대로다.
7. **삭제.** 페이지 루프, `RelatedSelection`·`EntrySelection`, `selection_schema`, `_validate_selection`/`RELATED_SELECTION_INCOMPLETE`, 페이지용 `catalogue`(paths 포함) 목록.
8. **coverage 기록.** 페이지별 `selections` 대신 `{"role": "SUBJECT_RESOLUTION", "segment_ref", "mechanical_subject_refs", "resolved_subject_refs", "mentions"(개수)}`.
9. **공통 fixture.** gridCases의 SETTING 기대값을 `gridVersion` 2, 구간별 `PLANNER→SUBJECT_RESOLUTION→COVERAGE`, `segments` 다음 `segmentSubjects`로 바꿨다(이름이 있는 사례 `unicode-whitespace-repeated-name-and-clues`만 `["S1"]`). TYPO 기대값은 1 그대로. `stagePayloads.RELATED_SELECTION`을 `SUBJECT_RESOLUTION`(TSEG1, 공통 계약의 mentions 예시)으로 바꾸고 `progressiveSourceGrid`도 v2·단계 이름을 고쳤다. 기존 키 순서·2칸 들여쓰기를 유지했다(json 재직렬화가 원본과 byte 단위로 같음을 먼저 확인).

## 미검증·남은 문제

- **실제 모델 재실행: 리뷰어 확인 예정.** 대규모 작품 재실행과 실제 Java↔Python HTTP 계약 테스트(`ValidationExecutionHttpPostgresIntegrationTest`, 합성 provider `--subject-mentions none|resolved|null`)는 이 브랜치에서 실행하지 않았다.
- 지칭 해소 품질(놓친 대명사·호칭, 잘못 연결한 주체)은 미측정이다. 놓치면 그 주체의 항목이 COVERAGE에 빠지고, 잘못 연결하면 항목이 더해질 뿐 판정은 JUDGE가 따로 한다.
- 기계 매칭은 정규화하지 않아 이름이 다른 단어 안에 나와도, 동명 주체도 함께 매칭된다(과포함 방향). 한 주체의 항목이 매우 많으면 COVERAGE 입력이 여전히 클 수 있다.
- 공통 fixture의 `segmentSubjects`(특히 baselineEntries 없는 사례의 빈 배열)는 Backend 구현과 대조 전이다. 리뷰어가 두 저장소 사본을 diff한다.
