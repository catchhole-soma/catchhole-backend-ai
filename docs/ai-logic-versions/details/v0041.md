2026-11-02 11:04 KST 운영 읽기 전용 집계에서 선정 캠페인은 660회차 중
472성공·9실패·179대기였다. 관계 비교 7건은 provider 응답 후 검증 실패였으나

- `relationship_comparator.py`: 전체 prompt가 64k 이내면 기존 단일 호출을 유지한다.
  초과할 때만 새로운 관측 O와 보류 H의 가능한 인물 쌍 교집합으로 연결 성분을
  만들고 관련 전체 슬롯·원래 참조/순서/근거를 투영한다. H를 거친 간접 연결도
  같은 성분에 보존한다. O가 없는 H 성분은 이번 prompt에만 빠지고 저장된 H는
  소비·삭제하지 않는다. 한 성분도 상한을 넘으면 호출 전에 실패한다.
- 모든 성분을 먼저 검사하고 입력 한도 안에서 탐욕적으로 묶는다. 최대16개 순차
  호출만 허용하며 결과를 결합한 뒤 원래 전체 문맥으로 schema512·coverage·슬롯을
  다시 검증한다. 부분 저장·원문 절단·응답 보정 호출은 없다.
- `relationship_diagnostics.py`와 pipeline/전용 Worker: 고정 원인20개와 단계2개를
  보존한다. provider 예외 문자열 대신 안전한 고정 메시지와 원래 실패 분류만
  runner에 전달한다. 캐릭터·세계관의 실패 분류와 검증은 변경하지 않는다.
- 전용 claim만 `supportsRelationshipRecovery=true`를 보낸다. Java가 고정 캠페인의
  적격 서비스 부담 실패 회차를 한 번만 복구하고 저장된 검증 관측으로 새 PREPARED
  Job을 준비한다. 이 기능은 일반 사용자 부담 분석을 재시도하지 않는다.

## 배포와 다음 확인

Java의 V105·복구 admission·진단 수신부터 배포하고 이 Worker를 다음에 배포한다.
구 Worker는 복구 지원을 광고하지 않아 새 API만 먼저 배포돼도 복구는 시작되지 않는다.
새 Worker claim으로 적격 실패 회차를 한 번만 재개하며 자동 반복 실패/무한 재시도는 없다.
계약/순서/공개 generation/서비스 부담 사용자 차감0을 운영 집계로 다시 검증한다.
실패가 남으면 새 고정 진단으로 원인을 확인하고 검증을 느슨하게 풀지 않는다.

별도2작품의10대기회차는 선행 일반 분석 실패를 기다리는 PENDING 작업 때문에
막혀 있다. 관계 복구는 일반 분석의 재시도·취소·사용자 비용 결정을 대신하지 않는다.
모든 회차와 작품 공개가 끝나기 전에는 전체 백필 완료를 선언하지 않는다.
실모델 품질 재평가는 담당 Codex가 배포 뒤 관계·근거 표본을 승인 범위에서 확인하며,
정량 비교가 필요하면 같은 입력/모델/judge로 별도 평가한다.
