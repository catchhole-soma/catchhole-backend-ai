## 변경 내용

v0051 머지 뒤 검토에서 찾은 일곱 문제를 프롬프트 문구로 고쳤다. `_COMMON`·`PLANNER_SYSTEM`·`SCHEMA_VERSION`·`app/validation/schemas.py`·`judging.py`·Java wire·예산·호출 상한·TYPO 프롬프트·운영 모델 설정은 바꾸지 않았다.

| 번호 | 문제 | 처리 |
| --- | --- | --- |
| 1 | CONFLICT와 SUSPECTED_CONFLICT의 경계가 글로 정해지지 않음 | 판정 절차 4단계에 같은 시점 규칙을 둔다. 저장된 현재값은 지금의 값이고, 지금 서술·이미 확정된 과거 사실·시간이 지나도 바뀌지 않는 속성은 같은 시점이다. 지금과 다른 과거 시점의 서술이나 원문·설정집에만 있는 기존 값은 변화·예외를 확인한다. 결론 정의는 이 단계를 가리키기만 한다. `db_evidence_sufficient`도 4단계의 확인이 필요하면 false다 |
| 2 | Worker가 질문을 실패시키는 출력 규칙 누락 | `출력 필드(DECIDED)` 블록 신설. `target_spans`, 상위 `evidence_refs`(충돌·의심은 B 또는 E 필수), `completion` 네 항목의 참조, FOLLOW_UP의 reason을 적었다 |
| 3 | 공통 머리말의 quote·TSEG 규칙이 판정 입력과 맞지 않음 | `JUDGE_SYSTEM`을 `_COMMON`을 잇지 않는 독립 문자열로 바꾸고 판정 전용 머리말을 둔다. `_COMMON`은 PLANNER만 쓴다 |
| 4 | `disagreements` 기록이 Worker에서 확인 필요로 바뀌는데 모델이 모름 | 같은 시점·조건에서 양립할 수 없고 그 때문에 기준을 정할 수 없을 때만 쓰도록 좁히고, 이야기 진행에 따른 변화를 제외했다. 명시 정정이 없으면 작가 확인 필요로 게시된다는 결과를 알린다 |
| 5 | Worker에게 하는 말 7곳 | 모델의 행동이나 결과 설명으로 바꿨다. 남긴 결과 설명은 근거 문장 없는 충돌의 NO_CONFLICT 게시와 OPEN SUSPECTED 뒤의 변화 검색 두 가지다 |
| 6 | 같은 규칙의 반복 | 규칙마다 한 자리에 두고 순서를 역할·입력·범위 → 출처·settings → 절차 → 충분성·읽기 요청 → 결론 → 해석 → 영향 → 작가 문구 → 출력 필드로 정리했다 |
| 7 | 의심 판정의 reason이 확정과 같음 | SUSPECTED_CONFLICT는 두 문장 뒤에 `그 사이에 바뀐 기록은 찾지 못했어요.`를 붙인다 |

문자열 측정(v0051 → v0052): 글자 수 8,507 → 8,480, 줄 수 64 → 47, `다른 속성` 4 → 2, `비교 기준` 4 → 2, `Worker` 7 → 2, `basis_quotes` 9 → 6, `글자 그대로` 4 → 2. 기존 값을 A, 이번 값을 B라고 부르던 표기는 settings 행 참조 B1과 겹쳐 `기존 값`·`이번 값`으로 풀어 썼다. 테스트가 고정한 문구는 하나도 고치지 않았다.

## 남은 검증과 결정

- 웹 전체 재검사는 미측정이다. 합성 회귀와 표본 재생은 FINAL 단일 호출만 보므로 OPEN의 FOLLOW_UP, Worker의 변화 검색 삽입, 근거 없는 충돌 해제까지 포함한 흐름은 실제 모델로 확인하지 않았다. 같은 웹 원고로 확정/의심 분포와 정상 문장 유지를 확인한다(담당 mkshie).
- `disagreements`를 쓴 응답이 없어 범위를 좁힌 효과는 미측정이다.
- 이번 변경 밖의 결정으로 남긴 것: 근거 문장 없는 충돌을 NO_CONFLICT로 바꾸는 대신 호출 여유가 있으면 FINAL로 다시 물을지(운영 `BASIS_QUOTES_DROPPED`·`*_QUOTE_MISSING_CLEARED`를 먼저 본다), 명시 정정 없는 `disagreements`를 NEEDS_CONTEXT로 바꾸는 Worker 규칙을 유지할지, settings에 작가가 확정하지 않은 값이 섞일 수 있다면 `작가가 확정한 현재값` 표현을 `저장된 현재값`으로 낮출지.
