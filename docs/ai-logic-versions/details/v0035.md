### 검증한 의미

선정 밖 계정은 제외하고 bootstrap 반복은 중복 등록하지 않는다. 1화 처리 후 새 core3화를
추가해도 2→3 순서로 진행하며 모두 끝나기 전 공개 세대는0, 완료 후1로 바뀐다.
1·2·3화 각각 cutoff 관계가 보이고 기존 캐릭터·세계관·후보·청크 생성은0이다.
raw 사용량과 사용자 차감 분리를 실제 Java 토큰 원장/HTTP로 확인했다.
Java는 배포 전에 성공한 회차, 동일 원문의 관계 호출 원장이 있는 회차, 중간 삽입에 따른
후행 재비교를 서비스 부담으로 처리한다. 위 새 3화의 220 차감은 기존 관계 호출이 없는
최초 실행 사례이며 운영상 재작성 비용과 구분한다.

### 원문 읽기 취소·종료 리뷰 보완 — 2026-10-31

[AI #108 리뷰](https://github.com/catchhole-soma/catchhole-backend-ai/pull/108#discussion_r4430155523)에서
지적한 기본 thread pool 사용을 제거했다. `asyncio.to_thread`로 시작한 원문 읽기는
heartbeat가 Job을 취소해도 계속 실행되어 다음 Job의 읽기와 겹칠 수 있었다.
이제 Worker가 기존 `BlockingIoExecutor`를 소유하고 `AI_WORKER_BLOCKING_MAX_WORKERS`
설정(운영1)으로 원문 읽기·순수 청킹을 실행한다. Job 취소는 바로 전파하지만 취소된
읽기도 같은 pool 한도에 남고, `aclose()`는 남은 읽기를 기다려 executor를 정리한다.
다른 소유 자원 종료가 실패해도 executor 정리를 시도한 뒤 최초 오류를 전파한다.
모델·프롬프트·입력·원문 검증·서버 lease 및 실패 보고 정책은 바꾸지 않았다.

이벤트로 첫 S3 읽기를 붙잡고 heartbeat 실패→Job 취소→다음 읽기 제출→종료를
재현했다. 기존 코드에서는 종료가 읽기를 기다리지 않아 새 회귀가 실패했다.
보완 후 최대 동시 읽기1, 취소 Job 완료/실패 게시0, 다음 Job 완료1, 남은 읽기0을
확인했고 provider 종료 오류 때도 executor가 닫히는 별도 회귀를 추가했다.
검증은 합성 저장소·이벤트·가짜 provider만 사용했으며 실제 S3/LLM/운영 실행은 없다.

- 집중: 관계 Worker·executor·runner 33 통과, heartbeat 4 통과.
- 전체 `python -m pytest -q`: **4,976 passed / 141 skipped / 기존
  StarletteDeprecationWarning 1**, 28.69초.
- 변경 Python 두 파일 `ruff check`, `git diff --check` 통과.
- 전체 로그: 로컬
  `.codex-artifacts/relationship-cohort-backfill-20261030/ai-bounded-source-pytest.log`.
