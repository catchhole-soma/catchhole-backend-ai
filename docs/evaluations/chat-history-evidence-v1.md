# 이력과 직접 근거 — 회귀 사례와 질문 검증안

2026-10-14 · #247 · AI PR #80 보완. 합성 자료의 코드 검증과 실제 모델의 의미 판정을 구분한다.
이 문서의 인물·수치·원문은 테스트용 합성 자료이며 사용자 원고·개별 응답을 보관하지 않는다.

## 확인한 결함과 수정

일반 원문 답변의 `answeredFacets`는 답한 정보 종류이고 `unansweredRowRefs`는 아직 전부
설명하지 못한 기록이다. 앞서 일부 기록의 시점·경위를 확인한 것만으로 모든 기록의 질문이
해결되었다고 보아, 정상적인 PARTIAL을 거절하는 계약 결함이 있었다. 합성 이력 5행 중
4행의 근거를 제공한 답변으로 검증 재시도 뒤 PROVIDER_FAILURE를 재현했다.

COMPLETE는 미확인 정보 종류·미답변 행·충돌이 모두 없을 때만 허용한다. 부분 답변 병합과
현재 조건 후처리에서도 미답변 행을 보존한다. 부분 답변끼리 결합할 때는 다른 행에서
같은 정보 종류를 찾았다는 이유로 앞서 검증한 설명을 버리지 않는다. 최신 답변이 해당 행의
요청 정보를 모두 확인하고 미답변에서도 제외한 경우에만 과거의 미확인 표시를 해제한다.

분류 지침은 값·이력에 인용을 붙이는 요청과 원문에서 이유·과정을 해석하는 요청을 구분한다.
전자는 HISTORY + sourceNeed NONE + includeEvidence true + FACTS로 기존 조회를 재사용한다.
의도 해석 후 항목이 명확하면 별도 답변 생성·검색·임베딩 없이 기록과 직접 근거 참조를 반환한다.
직접 경로의 실제 인용문은 Spring이 검증·연결한다. Python이 인용을 새로 작성하지 않는다.

직접 근거를 요청했으나 확인하지 못한 행은 기록을 유지하고 `원문 미확인`을 표시한다.
근거 미요청에는 이 표시를 붙이지 않는다. 파기·변경·상한·저장소 실패 안내를 기존 계약대로 유지한다.
검증 실패 로그에는 목적·schema·시도·오류 종류·고정 코드 위치만 남기며 질문·원문·생성 응답·ID는 남기지 않는다.

## 자동 회귀 범위

- `tests/test_chat_history_evidence.py`: 여러 페이지, 원문 일부/전체 누락·파기·변경·장애,
  출처 범위, 직접 근거 한도, 근거 미요청, 현재 수동 수정값과 이력 전용·삭제 기록, 같은 값 재기록.
- `tests/test_chat_hybrid_partial_rows.py`: 미답변 행과 미확인 facet의 독립성, ACTUAL 상태,
  잘못된 R/E·facet·허위 COMPLETE 거부, 최종 원문 변경 보류, 병합·조건 후처리의 미답변 보존.
- `tests/test_chat_validation_diagnostics.py`: JSON/schema/후속 계약 오류 구분, 민감값 미노출,
  재시도 성공·소진, 호출 한도, provider 장애와 검증 오류 구분.

고정 모델 출력을 입력한 실제 오케스트레이션·검증·정산·outbox의 연결 테스트다.
실제 모델이 아래 질문을 올바르게 분류한다는 정확도 측정은 아니다. 최신 실행 수와 복원 SHA는
[v0010 상세](../ai-logic-versions/details/v0010.md)에 남긴다.

## 함께 확인할 질문과 판정 기준

| 질문 예시 | 확인할 점 | 검증 구분 |
| --- | --- | --- |
| 세린의 기력 수치가 어떻게 바뀌었는지, 각 기록의 원문까지 전부 보여줘. | HISTORY와 직접 근거 첨부. 일부 원문이 없다고 기록 전체를 버리지 않는다. | 합성 경로 검증, 실제 분류 재평가 필요 |
| 20~40화에 기록된 기력 변화와 원문만 보여줘. | 항목 탐색·이력·원문 모두 같은 허용 출처 범위를 지킨다. | 합성 경계 검증 |
| 현재 기력과 과거 변화 기록을 구분해서 보여줘. | 현재 수동 수정값을 과거 인용으로 정당화하지 않는다. | 합성 경계 검증 |
| 같은 수치가 다시 기록된 회차도 빠뜨리지 말아줘. | 같은 값의 별도 기록을 유지하고 실제 상승으로 꾸미지 않는다. | 합성 표시 검증 |
| 기력이 실제로 증가한 횟수는 몇 번이야? | 이력 건수와 수치 증가 횟수를 구분한다. 전후값·삭제·회상·수동 수정·부분 조회를 고려해야 한다. | 추가 의미/집계 평가 필요; 현재 정확성 보장 안 함 |
| 기력이 왜 증가했는지 원문과 함께 알려줘. | WHY를 원문으로 확인한다. 수치 차이·사용 장면만으로 원인을 만들지 않는다. | 부분 원문 계약 검증, 실제 의미 평가 필요 |
| 그중 원문을 못 찾은 기록도 빼지 말아줘. | 이전 대상은 문맥에서 찾되 이번 자료를 다시 읽고 누락을 표시한다. | 직접 경계 검증, 실제 후속 지칭 평가 필요 |
| 35화 당시의 기력은 얼마였어? | 출처가 35화인 기록과 그 시점의 상태 복원을 혼동하지 않는다. | 상태 복원 미지원 안내 확인 대상 |
| 기력과 근력의 변화 내역을 각각 보여줘. | 두 항목의 이력·근거를 섞지 않는다. 복수 경로 선택과 범위 완전성을 확인한다. | 추가 복수 항목 의미 평가 필요 |
| 설정 화면에서 값을 수정한 뒤: 그 수치가 지금은 얼마야? | 과거 답변을 재사용하지 않고 현재값을 다시 조회한다. | 기존 최신값 재조회 회귀, 실제 지칭 평가 필요 |

같은 질문에 자료 조건도 바꿔 검증한다: 원문 전부 정상 / 일부 없음 / 전부 없음 / 파기됨 /
조회 중 변경 / 이력은 여러 페이지이나 근거 한도 도달. 운영 데이터를 훼손해서 조건을 만들지 않는다.
상한에 도달하면 확인 범위를 설명해야 하며, 성공 응답만으로 전체 원고를 빠짐없이 조사했다고 표시하지 않는다.

## 이번 실행의 한계

기존 실패 실행은 의도 해석 1회와 답변 2회가 모두 provider SUCCESS였으나 최종 실패했다.
원시 응답·검증 사유가 남지 않아 그 실행의 정확한 거절 필드는 확정할 수 없다.
일반 원문 답변에서 모델이 행을 아예 누락하고 미답변으로도 선언하지 않으면 전체 선택 행의
누락을 강제 검증하지 않는 기존 공백도 확인했다. 이 누락을 COMPLETE로 표시하는 합성 사례는
이번 수정의 해결 범위에 포함하지 않으며, 요청 대상 집합과 보조 조회 자료를 구분하는 후속 계약이 필요하다.
새 수정은 재현한 부분 답변 거절을 고쳤으며, 같은 실사용 질문의 실제 모델 재호출은 별도 검증으로 남긴다.
예상 밖 runtime 예외의 상세 구분과 기록 건수·실제 증감 횟수의 일반 집계도 후속 항목이다.
