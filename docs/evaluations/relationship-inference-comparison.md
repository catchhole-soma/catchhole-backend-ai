# Python·OWL 추론: 새 관계, 근거, 철회, 확장 비교

2026-11-19 · [Java #444](https://github.com/catchhole-soma/catchhole-backend-java/issues/444)

**명시한 규칙으로 새 혈연 조부모 관계를 만들고, 모든 독립 근거를 추적하며, 마지막 근거 철회와 사용자 삭제를 반영하는 기능을 두 방식 모두 구현했다.** 기본 51개와 확장 10개의 수작업 정답에 B/C가 각각 완전히 일치했다. 이번 세 규칙·합성 입력에서는 Python이 더 가볍고 빨랐고, OWL 운영 채택을 정당화할 추가 효과는 아직 입증하지 못했다. 이는 추론 기능의 실패나 온톨로지 전체에 대한 부정이 아니다. 의미 모델·규칙·근거 계약은 Python 구현에서도 활용할 수 있다.

## 2. 실제로 달라진 결과

`03_episode_three_confirmed`에서 직접 사실 `a1: 도윤→서연 혈연 부모`, `a3: 서연→하린 혈연 부모`가 있다. B의 인덱스 조인과 C의 OWL property chain 모두 입력에 없던 `도윤→하린 혈연 조부모`를 반환했다. proof의 전제는 `[a1,a3]`, 출처는 `[s1,s3]`다. 불확실한 소문 `a2`는 포함하지 않았다.

| 실제 사례 | 관측한 결과 |
| --- | --- |
| p01→p02→p03→p04 | 조부모의 지지 경로가 1→2→1→0개로 바뀜. 첫 경로 철회 후 나머지 proof만 남고 마지막 철회 후 결론 제거 |
| p05 | 양 부모 전제에 각각 독립 assertion 2개. 같은 조부모 결론에 정확히 4개 proof |
| p06→p07→p08 | 한 assertion의 복수 출처는 OR. 일부 철회는 proof 수를 늘리지 않고 살아 있는 출처만 남김. 마지막 출처 철회 후 전제 제외 |
| p09·p10·p11 | 미래 출처 제외, 다른 유효 경로 유지, 원문 파기만으로 현재 사실을 철회하지 않음 |
| p12·p13 | 부모 slot 전체 삭제는 새 assertion이 들어와도 역표현/의존 경로를 부활시키지 않음 |
| p14·p15 | 조부모만 삭제하면 직접 부모는 유지. 다른 중간 경로가 생겨도 해당 결론은 excludedDerivedRelations로 제외 |
| p16~p20 | 삭제 revision 전/후, 명시적 비활성화, 자녀 방향의 동등 삭제, 현재 정정 정책을 반영한 과거 독자 조회 구분 |
| x01·x02 | 손자녀는 조부모 결론을 전제로 소비. 네 독립 경로와 원래 assertion·출처까지의 추적 보존 |
| x05~x07 | 조부모/손자녀 중 어느 방향으로 삭제해도 두 표현을 함께 제외 |

추가 독립 회귀는 5인물·7assertion의 조합에서 4+1 경로, 6개 revision, 부모 삭제와 다른 중간 경로 생존, 새 근거 후에도 결론 삭제 유지, 3세대 관계 과생성 금지를 확인했다.

출력에 없는 관계를 전부 거짓이라고 해석하지 않는다. 시험한 입력과 규칙에서 얻은 결론의 정확한 전체 집합을 비교한 것이다. 원문이 실제로 참인지, 등장 인물 ID가 올바르게 해소됐는지, cycle/세대 conflict 표시가 빠짐없이 제공됐는지는 별도 선행 계약이다.

## 3. OWL 엔진과 직접 구현의 책임

| 책임 | B | C |
| --- | --- | --- |
| 사실의 회차·작품·맥락·유효 근거 선택 | 공통 정책 | 같은 공통 정책 |
| 새 관계 계산 | 선언된 원자/규칙을 인덱스로 조인 | owlrl 7.6.2가 RDF/OWL 공리의 closure 계산 |
| 모든 증명 경로 | 각 assertion 조합을 보존 | 별도 원 assertion 색인에서 독립 복원하고 엔진 결과와 exact 비교 |
| 근거 철회 | 직접 사실에서 새 인덱스 생성 | 직접 사실에서 새 그래프·closure 생성 |
| 사용자 관계 삭제 | 공통 정규화/전제·결론 제외 | 같은 공통 정책 |

C는 B의 결론이나 proof를 재사용하지 않는다. 반대로 “OWL이 proof와 삭제를 모두 자동 처리했다”고 말할 수도 없다. RDF의 중복 edge 합쳐짐을 보완하는 증거 색인과 도메인별 witness 복원을 직접 만들었다. closure에서 애플리케이션 관계가 누락되거나 예상 밖 연결·인물·동일성이 생기면 조용히 감추지 않고 실패한다.

철회는 두 방식 모두 **전체 재계산**이다. 기존 closure에 삭제를 증분 전파하는 truth-maintenance 엔진, 운영 이벤트 저장, DB 잠금·동시성/트랜잭션을 구현하지 않았다. 삭제는 현재 revision에 명시된 정책이고, 원문 인용의 파기와 구분한다.

## 4. 같은 규칙을 추가할 때의 실제 변경

기본 구현과 측정이 끝난 뒤 손자녀 역규칙만 추가했다. 무한 조상 탐색이나 자연어 추론을 함께 넣지 않았다.

| 변경 지점 | Python | OWL |
| --- | --- | --- |
| 의미 선언 | python_rules.py에 derived 조부모 원자를 소비하는 규칙 추가 | grandchild.ttl에 inverseOf 공리 추가 |
| 결론 실행 | 기존 Index·조인 실행기 재사용 | 기존 owlrl closure 재사용 |
| 제품 출력 | 선언의 kind/subtype/gap 활용 | 새 predicate→제품 GRANDCHILD_OF 매핑 추가 |
| 근거 | derived Candidate의 증명을 원래 assertion까지 펼치는 공통 처리 추가 | C의 조부모 witnesses에서 새 설명 경로를 독립 복원 |
| 평가 | 두 방식 모두 rulePath·intermediateRelations를 검증하는 계약 확장 | 동일 |

OWL의 장점인 표준 공리 선언과 기존 추론기 재사용은 확인했다. 그러나 B도 규칙 선언과 실행기를 분리했으므로 단순 사례별 if 구현에 비해 불리하게 만들지 않았다. 세 규칙에서는 C의 앱 매핑·증명 코드가 없어지지 않았고 유지보수 총비용 감소는 측정하지 않았다. 변경 줄 수만으로 우열을 판정하지 않는다.

기존 51개 입력을 확장 실행한 결과에서 손자녀 행만 제외하면 기본 결과와 완전히 같다. 기본 프로필은 여전히 손자녀를 출력하지 않는다. 손자녀가 늘어도 NEW_RELATION 수는 늘지 않는다.

## 5. 비용: 같은 데이터에서 각각 비교

macOS 26.6.2 arm64, Python 3.12.13, RDFLib 7.6.0, owlrl 7.6.2. 각 방식·자료당 별도 프로세스 4회, B/C 순서를 교대했다. 초기 계산과 출처 철회 후 전체 재계산을 모두 비교했다. 메모리 추적은 별도 실행이며 시간 측정과 겹치지 않았다. 측정 중 이 작업의 테스트를 동시에 돌리지 않았다.

아래는 **파싱·공통 적격성·모델 구성·추론·proof·출력 전체 시간의 중앙값(ms)**이다. 엔진 import와 JSON 파일 I/O는 제외하고 원자료에 별도로 기록했다. 공통 eligibility에는 구조 재검증과 복사도 포함한다. 재계산 입력은 첫 출처 철회와 snapshot revision 1 증가를 함께 적용한다. 큐레이션 사례에서는 이 증가로 예정된 삭제가 활성화될 수도 있다.

| 프로필 / 자료 | B 최초 | C 최초 | B 재계산 | C 재계산 |
| --- | ---: | ---: | ---: | ---: |
| 기본 / 51개 사례 | 6.008 | 462.048 | 5.368 | 465.883 |
| 기본 / 100개 직접 사실 | 4.464 | 40.244 | 4.355 | 38.877 |
| 기본 / 1,000개 직접 사실 | 60.522 | 336.194 | 55.545 | 335.035 |
| 손자녀 확장 / 같은 51개 | 6.410 | 498.339 | 5.674 | 493.729 |
| 손자녀 확장 / 같은 100개 | 5.254 | 45.012 | 5.129 | 42.983 |
| 손자녀 확장 / 같은 1,000개 | 68.740 | 376.168 | 68.317 | 371.521 |

51개 사례에서는 READY 조회마다 별도 그래프를 만든다. 규모 시험은 한 작품·한 맥락의 그래프 하나에 모든 사실을 넣는다. 따라서 “1,000개가 51개보다 빠르다”는 식으로 서로 다른 행을 비교하면 안 된다. 각 행에서 B와 C가 같은 입력·정책·전체 결과를 처리하는지를 비교한다.

기본 1,000개 입력의 초기 4회 범위는 B 58.480~62.597ms, C 321.835~342.118ms였다. 그중 추론 단계 중앙값은 B 2.165ms / C 265.594ms, proof는 B 1.505ms / C 6.267ms였다. B 전체 시간에서는 공통 입력 검사·복사의 비중이 크고 C에서는 범용 OWL closure의 비중이 크다. 이를 LLM 호출 시간이나 서비스 조회 지연으로 바꿔 말하지 않는다.

1,000개 직접 사실은 기본에서 자녀 역표현 1,000 + 새 조부모 500, 확장에서는 손자녀 500을 더 낸다. 전체 proof도 각각 1,500/2,000개로 저장·검사했다. 재계산 결과의 hash도 B/C 및 각 반복에서 일치한다.

규모 자료는 출력량이 선형으로 늘어나는 분리된 2단계 경로다. 많은 분기와 대체 근거가 겹쳐 proof 조합이 급증하는 큰 그래프의 비용은 이번 수치로 판단할 수 없다. 2×2와 4+1 경로는 정확성 경계로 따로 검증했다.

| 1,000개 입력 | B Python 할당 peak | C Python 할당 peak | B 프로세스 RSS | C 프로세스 RSS |
| --- | ---: | ---: | ---: | ---: |
| 기본 | 10.57MiB | 17.16MiB | 41.29MiB | 55.77MiB |
| 확장 | 11.82MiB | 16.69MiB | 42.70MiB | 55.70MiB |

Python 할당량은 초기+재계산을 수행한 별도 tracemalloc 실행 1회의 peak다. RSS는 추적기를 끈 4개 프로세스의 최대 상주 메모리 중앙값이며 라이브러리 로딩도 포함한다. GC와 측정 변동의 영향을 받으므로 확장의 C 값이 조금 작다는 것을 메모리 최적화 성과로 해석하지 않는다.

## 6. 검증 결과와 도입 판단

- 기본 24+27, 확장 10: B/C 각각 **61/61 exact 일치**. 제외 관계·전체 proof·전제 역할·출처·상태도 비교했다.
- 관련 테스트 **428 passed**(기존 fixture 검사 29개 + 새 검사 399개). 정답 삭제/변조/접근 차단, 입력 순서, 누락·추가·중복 출력, 손상된 규칙/엔진 결과, 저장 파일 변조도 포함한다.
- 전체 pytest **6249 passed, 186 skipped, 1 warning**(53.54s, 구현 `1671f2c`). skip은 실행하지 않은 검사다. warning은 기존 FastAPI/Starlette TestClient의 httpx deprecation이다.
- 깨끗한 환경에서 `pip install -e '.[dev]'`, 이어 `.[dev,ontology]`, `pip check` 통과. 변경 Python Ruff check/format, diff 검사 통과. 최종 원격 CI 결과는 PR 본문에서 연결한다.

규칙 추론 기능은 계획한 작은 범위에서 동작했고, 새 관계와 그 수명을 재현할 수 있게 되었다. 운영에 연결한다면 먼저 실제 소비자가 이 결과와 proof를 읽어 도움이 되는지 확인할 근거가 생겼다.

**구현 선택은 현재 범위에서 B를 우선 검토하는 것이 합리적이다.** C는 표준 선언·추론기를 사용할 수 있지만 이번에는 같은 기능에 더 많은 실행 비용과 별도 증명/정책 코드가 필요했다. 다양한 관계 규칙·타입 계층·외부 표준 데이터 연동 등 아직 시험하지 않은 요구에서 이 판단은 달라질 수 있다.

다음 단계는 실제 관계 snapshot을 읽기 전용으로 변환하는 adapter 하나와 소비자 질문 하나를 정해, 원래 관계도/검수/챗봇이 새 결론과 근거를 어떻게 활용하는지 평가하는 것이다. 이번 결과만으로 LLM 추출 정확도, 답변 품질, 운영 성능이나 장기 유지보수 비용이 개선됐다고 말하지 않는다. 현재 DB에 결과를 쓰거나 운영 기능을 켜지는 않았다.
