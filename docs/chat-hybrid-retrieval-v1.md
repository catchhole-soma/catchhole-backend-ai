## 2026-10-23 근거 보존·응답 복구 보완

현재 계획/답변 프롬프트는 `chat-hybrid-plan-v11`/`chat-hybrid-answer-v14`이다. 아래 OPT-31의 버전·실행 결과는 당시 기록으로 보존한다. 같은 v0023에서 근거 보존·coverage 복구에 이어 10/26 실행 실패 복구를 추가했다. 모델·검색 라운드·입력/근거/전체 호출 상한·Spring wire 계약은 유지하고 단계 출력과 종료 여유를 아래처럼 변경한다. 새 실제 평가 결과는 별도로 기록한다.

검증을 통과한 부분 답변이 사용한 원본 근거는 검색 청크 fingerprint 또는 직접 근거 identity로 보존한다. 재검색 결과를 조합할 때 이 근거를 우선하고, 모델 입력량을 맞출 때도 먼저 다른 후보를 제외한다. 필요한 보호 근거를 모두 담지 못하면 새 답변을 생성해 기존 답변을 대체하지 않고, 기존 부분 답변을 최종 재검증하는 경로로 돌아간다. 라운드별 E 번호는 다시 매기며 원본 identity와 혼동하지 않는다. 상세 선택·복구 규칙은 아래 요청 부분·근거 합성 절을 따른다.

명시한 모든 requestedParts를 답하고 미확인 행이 없으며 필수 현재 조회까지 충족한 일반 원문 답변은, 등록값과 원문의 차이 때문에 `coverage=PARTIAL`이어도 추가 검색 없이 종료할 수 있다. 충돌 표식과 각 출처를 유지하며 COMPLETE로 승격하지 않는다. 사건·조건·현재값 검사를 통과한 뒤 판단하고 항목별 `perItem`의 미확인 계약을 대체하지 않는다.

## 2026-10-15 조회·요청별 답변 보완

[조회 완전성·답변 표시 보완](chat-query-quality-v1.md)이 현재 focus/collection/perItem 계약과 조회 한도에 우선한다. 이 절의 당시 프롬프트는 hybrid 계획 v8·답변 v9, 실제 필드 선택 v1이다. 항목별 질문은 선택된 모든 논리 항목을 답변 또는 미확인 항목으로 덮어야 하며 사용 장면을 획득 과정으로 단정하지 않는다. ## OPT-31 후속 대화·원문 보완

[#247 OPT-31](https://github.com/catchhole-soma/catchhole-backend-java/issues/247)의 진단 뒤 추가한 현재 계약이며, 후속 실제 모델 검증은 [최종 코드·결과별 기록](chat-query-quality-v1.md#opt-31-후속-구현-검증--2026-10-15)을 따른다. 과거 실행 기록은 새 분류·원문 보완·복구의 검증으로 재사용하지 않는다.

- 인사·감사·챗봇 사용법만 있으면 `GREETING`·`THANKS`·`HELP` disposition으로 조회 필드를 비우고 서버 고정 존댓말을 기존 `ANSWER`로 반환한다. 사실 질문이 함께 있거나 작중 장면·능력 사용법을 묻는 경우는 조회 대상으로 계획한다. 최종 결과 계약과 사용량 원장은 유지한다. 대화 생략은 모델에 계속 알리고 공개 `CONVERSATION_LIMIT`는 `CLARIFICATION`에서만 표시한다.
- `sourceFallback`은 RDB 결과가 부족할 때 기존 원문 흐름으로 연결할 수 있다는 계획이다. `sourceNeed=NONE`이어도 true이면 원래 요구의 `requestedParts`가 필요하다. 실제 전환은 명시한 대상의 정상 `INSUFFICIENT_EVIDENCE`와 조회 지점의 typed gap을 함께 확인한다. 대상 미등록·관련 경로/값/행 없음은 gap으로 구분하며 공개 문구나 warning으로 추정하지 않는다. 명시적 부정을 포함한 정상 현재값 답변, collection/characterFilter, COUNT/DISTINCT, 명확화, 부분·잘린 조회, 자료 변경·원문 오류·실행 실패는 자동 전환하지 않는다. 등록 정보만 요청하면 planner가 false를 사용하고, 남은 모델·도구 예산이 없으면 등록 결과를 유지한다. 상세 조건은 [공통 보완 계약](chat-query-quality-v1.md#등록-정보-부족에서-원문으로-넘어가는-조건)을 따른다.
- 세계관 대상은 공통 resolver에서 전체 이름을 먼저 조회한다. 완전한 빈 결과에 한해 이름 끝의 공백으로 분리된 해당 분류 표시어를 한 번 제거하고 같은 분류로 다시 조회한다. 기존 후보·모호성·부분 조회·오류를 우회하거나 임의 별칭을 만들지 않는다.
- 초기 계획 v7은 requestedParts의 요구 범위·최초 획득과 sourceFallback 조건을 명시하고, 초기 보완의 답변 v8은 내면·행동·자기진술, 사건 전후와 인과 근거를 구분하도록 지시한다. 계획 검증 복구는 고정 규칙과 schema 필드 경로만 전달하며 계약을 완화하지 않는다. 기존 두 번의 시도·호출/토큰 상한, 실패 사용량 정산과 원문 인용 검사를 유지한다. 새 지침의 실제 의미 품질은 별도 검증 대상이다.

OPT-31 당시 계획 v8은 최초 습득 항목을 HISTORY로 조회하고 원문 PROCESS로 실제 획득을 확인하도록 지시한다. 현재 보유 목록 요청의 CURRENT와 구분하며 가장 이른 등록 기록이나 사용 장면을 실제 최초 획득으로 단정하지 않는다. 일반 원문 흐름은 직접 근거 조회 때 `3 * max_rounds + 2 + collection 검사 수`만큼 도구 여유를 남긴다. 기본 두 라운드에서는 collection 검사 외 8회분을 키워드·벡터·최종 검증에 남기며 기존 전체 상한은 유지한다. 실제 두 라운드 실행은 남은 시간·모델·도구 예산과 근거 상태에 달려 있다.

OPT-31 당시 답변 v9은 일반 `GroundedClaim.relatedFacets`로 질문에 직접 관련된 원문 맥락과 실제 요구 충족을 구분한다. 직접 답한 요구는 answeredFacets에, 관련 맥락만 있고 답하지 못한 요구는 missingFacets에 남긴다. 같은 claim의 answered/related는 겹치지 않으며 related는 coverage 충족으로 세지 않는다. 관련 맥락만 확인되면 PARTIAL로 유지하고 남은 예산에서 검색을 계속한다. 다른 claim이 그 요구에 직접 답한 경우는 실제 답한 주장으로 판단한다. related에도 정확한 supports.quote·동일 passage의 참조/위치 검사·최종 인용 검증을 적용하며, 항목별 itemAnswers의 기존 미확인 계약은 유지한다.

`hybrid.answer()`는 schema/계약 재시도 소진의 `ResponseValidationFailure`를 잡아 미검증 문장을 버리고 NONE으로 다음 검색 또는 기존 검증된 PARTIAL 보존 경로에 연결한다. 최종 근거 검사는 생략하지 않고 호출·검색·토큰·시간 상한도 늘리지 않는다. 전송/provider·출력 절단 복구·권한/조회 실패는 이 경로로 숨기지 않으며, 계획 등 다른 호출부는 기존 실패 처리를 유지한다. 후속 실제 모델 6건은 `77dc74e1df125dfec34fe609481d5881fbe45b57`에서 SUCCEEDED 6건, ANSWER 4건/INSUFFICIENT_EVIDENCE 2건이었다. 관련 원문 맥락의 ANSWER는 PARTIAL이며 정답률로 해석하지 않는다. 등록 정보 부족과 후속 재확인의 키워드·벡터 흐름을 확인했고 최초 습득의 HISTORY+PROCESS·두 검색 라운드는 실제 최초 입증에 이르지 못했다. 중간 `d1c8f6865e255a7a785c4020e3b0bfcede7b8a13`의 4건 중 성공 3건·실패 1건도 보존한다.

최종 제품 `265fc683d0f6d026c5ce860c9bb90afe06d24d83`는 미확인 요구의 문장·조사 분리와 EVIDENCE_LIMIT의 확인 범위 안내 통합만 추가했으며 실제 모델 호출은 반복하지 않았다. 최종 Python은 2,853 passed/54 skipped/기존 warning 1(11.99초), Ruff 통과다. 실제 호출·사용량과 남은 한계는 [공통 검증 기록](chat-query-quality-v1.md#opt-31-후속-구현-검증--2026-10-15)을 따른다.

실제 후속 6건에서는 관련 맥락 경로를 확인했으나 자연 발생한 모델 응답 검증 실패는 없었다. typed 검증 실패의 NONE 복구·기존 PARTIAL 보존은 합성 회귀로 검증했다. 최종 265fc68의 표시 변경은 전체 자동 테스트와 로컬 기동으로 확인했고 실제 모델 6건은 동일한 프롬프트·검색·검증 경로의 77dc74e에서 실행했다.

## 책임과 지원 범위

Spring은 사용자·작품 소유권, 실행 시도·허용 출처 범위, 사용량 예약·정산, 검색 인용 검증·사용 허가, 최종 결과 저장과 파기를 담당한다. Python의 챗봇 처리기는 질문을 해석하고 RDB와 원문에서 필요한 자료를 모으며, `app/retrieval`의 공통 조회·근거 합성은 답변 형식이나 오류 판정에 종속되지 않는다.

| 영역 | 제공하는 것 | 의미의 한계 |
|---|---|---|
| RDB 현재 설정 | 캐릭터 snapshot·현재 세계관 속성 | 현재 Fact 한 행이나 과거 상태 전체 복원이 아님 |
| 확정 이력 | 출처 회차로 제한한 등록 이력 | 출처 회차와 사건 발생 시점은 다름 |
| 직접 원문 | 등록 설정에 연결되어 유효성이 확인된 인용 | 능력 보유 근거가 획득 과정까지 설명한다는 뜻은 아님 |
| 검색 원문 | 현재 회차의 유효한 검색 청크·키워드·벡터·인접 문맥 | 검색된 일부 자료가 작품 전체 검토를 뜻하지 않음 |
| 미지원 | 업로드 설정집 검색, 과거 원문 버전, 특정 회차 당시 전체 상태, 원고/설정 수정 | #221의 미완료 출처 처리를 이용 가능한 것으로 간주하지 않음 |

기존 분석용 `episode_chunks`와 후보 source 연결은 유지한다. 검색은 GH239의 `retrieval_sources`·`retrieval_chunks`를 사용하며 분석용 6,000자 청크를 검색 크기로 다시 쓰지 않는다. 공통 검색을 소비하는 #66은 검사 대상 선정·검사 범위·오류 검증 문맥을 소유한다. 이번 챗봇 응답은 오류 리포트의 최종 충돌·심각도 판정이 아니다.

## 질문 한 건의 흐름

`HybridPlan`은 `rdbMode`와 `sourceNeed`를 독립적으로 표현하고 `sourceFallback`으로 등록 정보 부족 뒤의 보완 가능성을 표시한다. `rdbMode`는 NONE/CURRENT/HISTORY/CURRENT_AND_HISTORY/DIRECT_EVIDENCE/CHARACTER_LIST, `sourceNeed`는 NONE/SCENE/REASON/PROCESS다. 특정 회차 전체 상태 복원·지원 밖 요청·모호한 질문과 사실 조회가 필요 없는 인사·감사·챗봇 도움말은 disposition으로 먼저 구분한다.

1. Spring이 질문을 접수하고 인증된 작품, 실행 시도, 허용 출처 회차와 전체 호출/사용량 한도를 고정한다. Python은 모델 출력에서 회원·작품·실행 ID를 받지 않는다.
2. 질문이 현재 설정, 이력, 직접 근거, 장면·이유·과정 중 무엇을 요구하는지 확인한다. “현재 능력과 그것을 얻은 과정”처럼 두 요구가 함께 있는 경우 RDB 요구와 원문 요구를 모두 보존한다.
3. 이름/설정 조회는 GH236의 읽기 전용 도구와 RDB 경로와 공통인 대상 resolver를 사용한다. 이름을 지정한 세계관 대상의 `worldCategory`도 FIND에 적용하며 다른 분류의 동명 대상을 합치지 않는다. 단순 설정 질문은 충분한 등록값으로 종료할 수 있다. RDB hit는 장면·이유 요구의 충족 조건이 아니며, 등록된 대상이 없다는 이유만으로 원문에 없는 인물·사건이라고 단정하지 않는다.
4. `sourceNeed=NONE`이면 먼저 기존 RDB `answer_plan` 경로를 사용한다. 정상적인 등록 정보 부족이 위 sourceFallback 조건을 모두 만족하면 같은 실행의 선택 행과 남은 예산으로 `run_source(collect=false)`에 연결하며 등록 조회를 반복하지 않는다. 장면·이유·과정에서는 RDB 관련 행과 직접 근거를 먼저 모아 `GroundedAnswer`를 만든다. 직접 근거가 질문 전체를 설명한다고 판단되면 검색을 생략한다. 부족하면 1차 키워드+인접 조회 → 답변, 2차 벡터+인접 조회 → 답변으로 최대 두 라운드를 실행한다. 검색어·인물명은 현재 질문 또는 허용된 최근 대화에 관측된 표현을 검증하며, perItem 검색은 이번 실제 RDB에서 확인한 항목 표시명을 보충한다. 원문으로부터 새 이름/SQL을 만들지 않는다. 직접 근거의 회차 ID는 키워드 정렬 우선순위로 사용하고 검색 범위 필터로 고정하지 않는다. 따라서 처음 서버가 허용한 범위의 다른 회차도 후보로 유지하며 벡터는 그 허용 범위 전체를 조회한다. 현재 설정을 출처 회차 당시 상태라고 말하지 않는다.
5. 중복 청크를 합치고 질문 경로의 후보 선택 정책을 적용하며, 같은 원문 버전의 실제 겹침만 하나의 문맥으로 조합한다. 새 requestedParts 일반 원문 답변은 검색 순위를 우선하고 항목별 답변은 기존 회차 분산을 유지한다. 행·근거·회차별 수·인접 확장·문맥/출력 토큰·도구/모델 호출 한도를 함께 적용한다.
6. 답변에 사용할 원문 인용을 Spring의 실행별 검증 경로로 보낸다. 허용된 인용만 답변 자료로 사용하고, 결과에는 본문에서 실제 사용한 기존 직접 근거와 새 검색 인용을 각각 연결한다.
7. Python은 최종 답변에 사용한 검색 인용을 재조회·등록하고 직접 근거도 다시 읽어 같은 자료인지 확인한다. 최종 결과를 저장할 때 Spring이 검색 인용의 사용 허가와 현재 원문을 다시 검증한다. 무효 근거를 삭제하고도 남은 문장을 완전한 답으로 게시하지 않으며 이번 흐름은 변경된 근거를 발견하면 답변을 보류한다.

질문·설정값·원문의 문장은 자료다. 자료에 포함된 역할 변경, SQL/URL 실행, 다른 작품 조회 지시가 도구 권한이나 실행 범위가 되지 않는다. DB 쿼리는 개발자가 작성한 제한된 조회 코드만 사용한다.

## 요청 부분·동일 사건·지원 구절

새 원문 계획은 최대 네 개의 `requestedParts: [{ref: P1..P4, description}]`로 질문이 요구한 내용을 보존한다. 예를 들어 감정과 이후 행동의 영향은 서로 다른 요청 부분이다. `sourceNeed`는 여전히 검색 경로를 고르는 넓은 분류이며 모든 요청을 TIME/HOW/WHY/SCENE 중 하나로 압축하지 않는다. 새 계획의 `requestedFacets`는 빈 목록이고, 구형 저장 계획에는 기존 facet 호환 경로가 남는다. 답변의 기존 `answeredFacets`·`missingFacets`와 항목별 `facet` 필드가 새 계획에서는 P 참조를 사용한다. 요청 부분을 답변 또는 미확인으로 덮는 구조 검사는 의미적 정답을 보증하지 않는다.

`eventContext`는 현재 질문과 제한된 최근 대화에서 요청한 동일 사건을 유지하는 해석 문맥이다. 앞 질문이 첫 사건을 묻고 후속 질문이 그 뒤의 감정·영향을 물으면 그 사건의 제약을 유지하도록 지시하며, 사용자가 새 사건을 명시하면 최신 요청을 따른다. 이전 답변의 사건·회차는 미검증 힌트일 뿐 근거나 강제 회차 필터가 아니다. 이번 실행에서 DB·원문을 다시 읽는다. 답변 모델의 `eventMatch=MATCH/OTHER/UNCERTAIN` 중 OTHER/UNCERTAIN은 요청 사건의 확정 답으로 게시하지 않는다. 별도 `eventScope`·`eventStatus`는 실제 발생과 계획을 구분한다. 두 분류 모두 모델의 의미 해석 자체를 독립적으로 검증하는 장치는 아니다.

새 원문 답변의 주장과 항목별 답변에는 `supports: [{evidenceRef, quote}]`를 받는다. quote는 제공한 passage에서 그대로 복사한 지원 구절이다. `hybrid_grounding.py`는 해당 참조가 속한 passage 안의 정확한 일치를 먼저 검사한다. 정확한 일치가 없을 때만 개행과 그 주변 공백을 한 칸으로 표시한 형태에서 유일한 원래 구간을 찾고, 저장할 support quote를 그 구간의 원문으로 복구한다. 개행과 무관한 띄어쓰기·단어·구두점의 변경이나 의역을 고치지 않는다. 검사·복구는 동일하게 제공된 passage 안에서만 이루어지며 다른 passage로 이동하지 않는다.

보존한 원래 청크의 Unicode code point offset으로 실제 구절 전체를 덮는 참조에 연결한다. 같은 merged passage의 앞 청크를 지목했어도 실제 구절을 포함한 원본 청크로 연결하고, 구절이 경계를 넘으면 필요한 모든 원본 참조를 유지한다. 없는 구절·알 수 없는 anchor·중복 위치·참조로 덮이지 않는 구간은 거절한다. 최종 Spring wire 인용은 계속 원래 청크와 hash/offset/receipt 계약을 사용한다. 이 변경은 공개 인용을 지원 구절 길이로 자르는 기능이 아니다.

지원 구절 검사는 원문 존재·위치·참조 연결을 검증한다. 인과관계나 주장의 의미적 지지, 작품 전체 최초 발생을 자동 증명하지 않는다. 시점 답변에는 근거의 출처 회차와 확인한 사건 시점의 차이를 드러내도록 지시하며, 검색한 자료에서 가장 이른 관측을 작품 전체의 최초라고 단정하지 않는다. 이런 표현과 동일 사건 추적의 실제 품질은 별도 모델 평가 대상이다.

추가 검색은 미답변 요청 부분과 사건 문맥을 중심으로 수행한다. 새 requestedParts 일반 경로에서 검증을 통과한 직전 답변이 `NONE`이면 다음 벡터 라운드는 기존 키워드 후보 목록을 새 벡터 결과로 교체한 뒤 인접 문맥을 확장한다. 답하지 못한 이전 자료의 키워드 점수와 새 cosine 점수를 비교해 이전 자료가 공간을 계속 차지하지 않게 한다. 벡터 제외 조건은 현재 선택·보존된 근거 중 실제 모델에 노출한 청크 ID이며, 찾았지만 입력에서 제외한 후보나 모든 과거 노출 ID를 누적해서 제외하지 않는다.

검증 실패 뒤 복구용 `NONE`은 정상 `NONE`과 구분한다. 거절한 답변의 문장은 게시하지 않으며, 타입이 유효한 응답에서 위치를 검증한 지원 구절이 있으면 해당 원본 청크만 다음 검색의 우선 후보로 남긴다. 그런 힌트가 없으면 직전 문맥의 제한된 일부를 후보로 남긴다. 후보 보존은 답변의 사실성·요구 충족을 승인하지 않는다. 복구 우선 후보 수는 가용 검색 슬롯의 절반(최소 1개)으로 제한하고 새 벡터 후보에도 우선순위를 배분한다. 실제 포함 여부는 같은 전체 예산으로 결정한다. 검증된 `PARTIAL`이 사용한 근거는 이 복구 후보보다 먼저 배치하며, 기존 부분 답변과 E 참조 snapshot을 별도로 보존해 새로 확인한 부분과 병합한다. 인용이 겹침 경계를 넘으면 해당 원본 참조 전체를 보호한다. 직접 근거와 검색 문맥은 같은 전체 한도를 사용하며, 보호 근거를 담지 못하면 기존 검증된 부분 답변을 최종 재검증한다. 전송/provider·권한·출처 오류를 이 fallback으로 숨기지 않는다. 모델의 NONE 판정이 이전 자료의 무관함을 독립적으로 증명하지는 않으며, 후보 선택 보완만으로 초기 회수율이나 최초 사건 해석이 보장되지 않는다.

## 공통 검색 인터페이스

Python의 `RetrievalSearchService`는 `readiness`, `keyword`, `direct`, `neighbors`, `vector`, `revalidate`를 제공한다. `SearchScope`의 회원·작품·회차는 신뢰 서버 문맥에서 만들어야 한다. 서비스 자체가 임의 사용자 입력을 인증해 주는 API는 아니다.

- `keyword(scope, query, limit, preferred_episode_ids=())`: 최대 1,000자 검색어와 제한된 검색어 조합을 사용한다. 확인된 직접 근거 회차를 SQL 정렬에서 우선할 수 있지만 해당 ID 목록으로 검색 대상을 제한하지 않는다. 실제 준비된 유효 텍스트는 임베딩이 없어도 조회 가능하다. 검색어 또는 결과를 줄이면 한도를 표시한다.
- `direct(scope, chunk_ids, limit)`: 검색 청크 ID를 같은 유효성/권한 조건에서 확인한다. 분석 Fact의 source ID와 검색 청크 ID를 서로 대체하지 않는다.
- `neighbors(scope, seeds, radius, limit, include_episode_edges=False)`: 기본은 같은 출처·정책·버전의 현재 유효한 주변 청크만 확장한다. 챗봇 요구별 원문 경로만 opt-in으로 바로 전/후 회차 경계를 읽으며 권한·현재 원문·서버 회차 범위를 유지한다. 누락 회차를 건너뛰지 않고 유효한 chunk_count/index를 가진 경우만 경계 거리를 계산한다. 입력 seed 순위를 재검증 후에도 유지하고 seed 순위 → 해당 seed와의 거리 → 회차/청크 순서로 선택한다. 여러 seed가 공유한 인접 청크는 가장 앞선 seed에 한 번만 연결한다. 유효성·권한 필터와 seed 제외는 LIMIT보다 먼저 적용한다. 따라서 높은 순위 후보의 이웃이 거리 동률의 낮은 회차들 때문에 먼저 탈락하지 않는다.
- `vector(scope, query, embedding_client, limit)`: 준비 상태와 권한을 먼저 확인한다. 유효 벡터가 없으면 질문 임베딩 API를 호출하지 않는다. 모델/버전이 맞는 실행 계량 client를 주입하고 기존 `EpisodeChunkVectorSearchService`를 검색 repository adapter와 함께 재사용한다.
- `revalidate(scope, chunks)`: 결과를 다시 읽어 처음 관측한 원문/청크와 같은 자료인지 확인한다. 사용자가 없거나 작품 접근이 취소된 상태를 정상 빈 검색 결과로 바꾸지 않는다.

`SearchReadiness`는 출처 수, 텍스트 준비 출처/청크, 벡터 준비 출처/청크와 제한 사유를 구분한다. 텍스트 준비가 벡터 준비를 뜻하지 않고, 검색어 미일치·색인 일부 준비·원문 이용 불가도 서로 다르다. 초기 검색 순위·청크 800/100 정책은 실측 최적값이 아니다.

동기 DB 조회는 주입한 blocking runner로 이벤트 루프 밖에서 실행한다. HTTP runtime은 검색 DB에 `default_transaction_read_only=on`, 연결/SQL/풀 대기 각 5초, `pool_size=2`·`max_overflow=0`을 적용한다. 이 두 연결도 배포 전체 DB 연결 예산에 포함해야 하며, 기존 분석 Worker 동시성을 자동으로 늘리지 않는다.

## 유효성·중복 제거·문맥 한도

모든 조회에서 회원/작품 활성 상태와 귀속, 회차 보관·파기 예약, 현재 원문 key/hash/version, 청크 정책, 검색 범위를 확인한다. 벡터 조회에는 READY와 모델·임베딩 버전을 추가 적용한다. 키워드/직접/인접 조회도 다른 버전의 실제 벡터가 있는 청크를 정상 호환으로 간주하지 않는다.

`ChunkEvidence`는 원래 청크/회차 ID, 출처 회차, source key/version/hash, policy, 원문 code point offset, chunk hash, 텍스트, 검색 방식과 score를 보존한다. source key와 원문은 로그/metric label에 노출하지 않는다. `score`가 높다는 것은 답변을 의미적으로 입증한다는 뜻이 아니다.

`compose_evidence`는 다음 규칙을 적용한다.

- 같은 청크 ID·동일 fingerprint는 검색 방식만 합치고 하나로 취급한다. 같은 ID에 다른 텍스트/버전이 오면 충돌 자료로 제외한다.
- 먼저 원문 길이와 offset, UTF-8 SHA-256, 허용된 검색 방식과 유한 score를 검사한다.
- `priority_chunk_ids`에 명시한 ID 순서를 먼저 적용하고, 그 뒤 기존 retained 참조·직접 근거·나머지 순위 정책을 적용한다. 같은 위치·버전·원문인 다른 ID가 중복되면 먼저 명시한 priority ID를 대표로 보존하고 검색 방식은 합친다. priority와 retained에 중복 지정해도 한 후보로 처리한다. 우선순위가 유효성·충돌·개수·회차·토큰 검사를 우회하지는 않는다. 기본 `episode_round_robin=true`는 회차별 교대 선택이며 항목별 답변과 기존 호출이 사용한다. 새 requestedParts 일반 원문 검색만 false로 설정해 나머지 후보의 검색 방식·score·회차·청크 순위를 유지한다. 어느 정책도 전체 개수·회차별 개수·문맥 토큰 상한을 완화하지 않는다.
- 동일한 source fingerprint의 닿거나 겹친 slice만 합친다. 겹친 문자열이 다르면 임의로 보정하지 않는다. 합친 문맥도 원래 청크별 참조를 유지한다.
- 상한으로 제외한 청크, 유효성 실패, 충돌은 `limited`/제외 수에 남긴다. 텍스트를 몰래 자르거나 일부 자료를 전체로 표시하지 않는다. 토큰 예산은 문맥 본문용이며 system prompt·질문·schema·출력 여유는 조율 계층이 별도로 포함한다.

## Spring 검색 인용 계약

`POST /api/internal/v1/chat-runs/{id}/retrieval-sources`는 기존 내부 API key와 `X-Chat-Capability`·`X-Chat-Runner`를 요구한다. 유효한 현재 실행과 서버가 고정한 작품·회차 범위 안에서만 검증한다. 이 경로는 모델이 임의 원고를 읽는 공개 도구가 아니다.

| 자료 | 형태 |
|---|---|
| 요청 | `{sources: [RetrievalReference]}` — 1~12개 |
| 응답 payload | `{schemaVersion: 1, sources: [검증한 같은 참조]}` — `CommonResponse`로 감쌈 |
| 최종 결과 | 기존 `outcome/text/sources/limitations` + 선택적 `retrievalSources` |

`RetrievalReference`는 `chunkId`, `episodeId`, `sourceEpisodeNo`, `sourceHash`, nullable `sourceVersion`, `quote`, `startOffset`, `endOffset`를 가진다. sourceHash는 소문자 64자리 SHA-256이다. 위치는 회차 원문 전체 기준 **0-based Unicode code point, 끝 제외** 구간이며 Python 문자열 인덱스와 같은 단위다. Java UTF-16 char 길이나 UTF-8 바이트 위치를 사용하지 않는다. 인용은 공백이 아닌 텍스트이며 최대 4,000 code point, sourceVersion은 최대 100자다.

검증에서는 같은 작품/회원·출처 범위, 현재 DB manifest, 실제 청크 hash/slice, 실제 저장소 원문 hash와 slice를 대조하고 읽은 뒤 DB 메타데이터를 다시 확인한다. `CHAT_RETRIEVAL_EMBEDDING_VERSION` 기본값은 `v1`이며 현재 policy `cl100k-800-100-boundary-v1`·model `text-embedding-3-small`과 맞춘다. 유효한 준비 청크의 embedding=NULL은 키워드/인접 인용을 위해 허용한다.

성공 시 전체 인용 필드를 포함하는 실행 receipt를 남긴다. 기존 `sources`는 `CHARACTER_EVIDENCE`/`WORLD_EVIDENCE` 등 기존 typed 참조를 유지하고, 검색 청크를 Fact ID로 가장하지 않는다. `retrievalSources`는 생략/빈 목록이 구형 결과와 호환되며 Java는 빈 목록을 JSON에서 생략한다. 같은 source를 받았다는 것만으로 임의 quote/offset을 바꿔 사용할 수 없다. 최종 `finish`는 receipt와 실제 현재 원문을 다시 대조한다.

`CHAT_SCOPE_INVALID`(403)는 범위·stale·인용 불일치 등 인용을 사용할 수 없는 상태이고 `CHAT_SOURCE_UNAVAILABLE`(503)는 저장소 읽기 장애다. 두 상태를 근거 없음이나 사용자 quota 부족으로 바꾸지 않는다.

공통 fixture는 `retrievalRequest`, `retrievalResponse`, `result` 세 최상위 항목을 가진다. fixture 원문은 `민수는 동료를 지키기 위해 흑염🔥을 사용했다.` 한 문장 전체이며 offset은 `[0, 25)`다. emoji로 UTF-16 길이 26과 code point 길이 25의 차이를 검증한다. `sourceHash`는 실제 합성 문장의 UTF-8 SHA-256이며 실제 사용자 자료가 아니다. `result.sources=[]`는 기존 직접 근거를 이 예제에서 사용하지 않았다는 뜻이다. 본문에서 사용한 검색 인용 한 개가 `result.retrievalSources`에 그대로 들어간다.

## 현재 저장소 검증의 제한

현재 Java `ObjectStorageService.getText(key)`는 저장소 응답의 실제 S3 VersionId를 반환하지 않는다. 따라서 `sourceVersion`은 DB의 현재 manifest와 대조하지만, S3 응답 자체가 그 versionId인지 확인했다고 표현하면 안 된다. 실제 읽은 본문을 SHA-256과 원문 slice로 검증하여 다른 내용의 재노출을 차단한다. 동일 본문의 다른 S3 version을 식별하는 보장은 없다.

원문당 `getText` 전체 다운로드 이후 UTF-8 최대 2,000,000 bytes(경계값 포함)와 hash를 검사한다. 신규 업로드 글자 수 제한보다 큰 기존 원고도 Python 색인과 같은 byte 상한 안에서는 검증한다. 신규 업로드·수정 정책, 인용 4,000 code point 상한과 원문 offset은 바꾸지 않는다. 인용이 작아도 원문 전체를 읽으며, Java의 이 상한은 전송 바이트·다운로드 중 메모리 사용량의 사전 제한이 아니다. Python 색인은 저장소 읽기 자체에도 같은 byte 상한을 전달한다. 검증 한 번 안에서는 같은 회차의 원문을 재사용하지만, 인용 등록과 최종 finish에서 다시 읽는 비용이 있다. S3 장애/지연과 DB 잠금 점유를 실제 부하에서 별도로 확인해야 한다. 작은 quote 상한을 저장소 I/O 상한이라고 설명하지 않는다.

회차 수정·삭제·교체 이벤트에서 작품 전체 채팅 질문/답변/receipt를 무효화하는 GH237의 보수적인 정책을 유지한다. 출처 검증 후 파기되었으면 완료 결과를 게시할 수 없어야 한다. #241이 대화 테이블에 사본을 만들 때에도 같은 정리를 연결해야 한다.

## 의미 검증과 평가 설계

원문 답변의 `GroundedAnswer`는 COMPLETE/PARTIAL/NONE coverage, 최대 8개 주장과 최대 4개 등록값/원문 불일치 참조를 받는다. LLM은 짧은 자연어 주장과 요청 내 E*/R* 참조를 선택하고, 코드는 실제 quote와 RDB 값을 붙인다. 최종 본문에 사용하는 근거만 typed source 목록에 남기고 길이 초과 시 주장을 남긴 채 인용만 잘라내지 않는다. 본문과 인용을 함께 담지 못하면 질문 범위를 좁히도록 근거 부족 결과를 반환한다.

답변 v9은 직전 v7에 적용한 `qa_prompts.py`의 공통 `ANSWER_STYLE_INSTRUCTIONS`를 유지한다. 일반 claim과 항목별 설명은 목록 안에서도 존댓말(`~습니다`·`~요`)로 작성하고 사용자·이전 대화의 반말을 따르지 않는다. 저장값·고유명사·정확한 quote/`supports.quote`는 말투 변경 대상에서 제외한다. 등록 설명·현재 조건·이력 조건 프롬프트에도 같은 지침을 적용한다. 생성 뒤 말투 정규식 재작성이나 교정용 추가 LLM 호출은 없고 정산·지원 구절 검사와 원래 청크 인용 계약은 유지한다. 직전 말투 보완은 계획 v6/답변 v7이었으며, OPT-31 초기 보완은 계획 v7/답변 v8, 당시 최종 계약은 계획 v8/답변 v9로 prompt cache key를 구분했다. 최신 cache key는 문서 첫 절에 기록한다.

구조 검증과 의미적 지지는 다른 결과다. 올바른 청크 ID와 실제 quote가 있어도 질문의 이유·과정을 설명하지 않을 수 있다. 실제 원문에 있는 인물 이름만 같다는 이유로 인용이 답변을 입증한다고 판정하지 않는다. 현재 runtime은 참조의 존재·원문 일치·범위를 결정적으로 검증하지만, 생성한 claim의 의미를 별도 entailment 모델이나 판정기로 자동 검증하지 않는다. 명시 요청 부분이 있는 일반 원문 답변의 coverage는 요청 부분·행·인용 검사를 통과한 구조에서 파생하며, enum 불일치만으로 올바른 주장과 인용을 다시 생성하게 하지 않는다. 모든 요청을 답하고 미확인·충돌이 없으면 COMPLETE, 확인한 주장/충돌이 있지만 미확인이나 충돌이 남으면 PARTIAL, 지원된 답변이 없으면 NONE이다. 실제 어떤 주장이 요구를 답했는지의 의미 판단은 여전히 모델에 의존하므로 이 상태가 의미적 정확성 인증은 아니다. 상시 judge를 추가하지 않은 한계는 합성 기대 근거 검토와 후속 실제 모델 평가에서 따로 측정한다.

| 합성 사례 | 검사할 동작 |
|---|---|
| RDB 현재 능력만 요청 | 검색/질문 임베딩 호출 없이 등록값 응답 |
| 현재 능력과 획득 과정 동시 요청 | RDB 값을 보존하면서 부족한 과정 근거 추가 조회 |
| RDB에 없는 장면/대상 | 원문 조회 경로가 존재하며 RDB miss를 존재 부정으로 변환하지 않음 |
| 직접 원문으로 과정까지 확인 | 불필요한 확대 검색 여부를 구분 |
| 키워드/벡터가 같은 청크 반환 | 중복 제거, 원래 ID와 source version 유지 |
| 한 회차에 유사 청크 집중 | 회차 다양성과 원래 허용 범위를 함께 준수 |
| 유효한 ID·quote지만 질문과 무관 | 구조 검증은 통과할 수 있지만 기대 답변/관련성 검토에서는 실패 |
| 근거에 없는 동기/원인 추가 | 평가에서 근거 없는 주장으로 실패 표시; runtime의 자동 의미 검출은 미구현 |
| 과거 출처/회상·허용 회차 밖 정답 | 출처 번호를 사건 시점으로 바꾸거나 검색 범위를 확대하지 않음 |
| 텍스트만 준비·벡터 없음 | 키워드는 사용 가능, 질문 임베딩 호출 생략, 준비 범위 표시 |
| 조회 중/검증 후 삭제·교체 | 무효 인용 및 이를 근거로 한 답변 게시 차단 |
| 모델/정책 불일치·파기 대기 | 같은 유효 검색 공간에 섞이지 않음 |
| provider 실패·quota·도구/문맥 상한 | 원인 구분, 제한 표시, 실패 호출 사용량 보존 |

평가층은 (1) 계약/분기 단위 테스트, (2) 격리 PostgreSQL의 실제 필터·정렬·벡터·유효성 검증, (3) Spring/Python HTTP·receipt·결과 저장·정산 연결, (4) 합성 질문에서 기대 주장/근거를 사람이 검토하는 것으로 구분한다. 고정 model JSON을 재생해 얻은 통과율은 **fixture의 연결 동작 검증**이며 실제 배포 모델의 분류·관련성·답변 품질·비용 측정이 아니다. 별도 judge를 상시 호출하는 설계나 실제 모델의 정확도 수치를 가정하지 않는다.

`tests/fixtures/chat-hybrid-v1.json`은 위 wire fixture와 다른 **합성 질문 재현 자료**다. `valid_id_unrelated_claim_negative_control`은 “비가 내렸다”는 유효한 원문을 E1로 제공하면서 “반지를 강물에 던졌다”는 지지되지 않는 model claim을 의도적으로 주입한다. 현재 구조 검증에서는 ANSWER가 만들어지는 사실을 확인하고, `semanticExpected=UNSUPPORTED_CLAIM`·`qualityMeasurement=false`로 별도 표시한다. 이는 실제 모델에서 관측한 실패율이 아니며 테스트 PASS도 답변 품질 PASS가 아니다. 유효 인용만으로 의미적 정확성을 보장할 수 없다는 경계를 드러내는 인위적 대조군이다.

10개 질문의 근거/주장, 적절한 처리 경로와 보류 원인은 AI 저장소의 `docs/evaluations/chat-hybrid-v1-offline-review.md`에 내부 검토로 기록한다. 지지되는 작성 사례 7개·타당한 보류 2개·의도적 의미 실패 대조군 1개이며 실제 모델 정확도 비율로 집계하지 않는다. 빈 키워드 결과나 무관한 weather 반환은 검색 대역에 주입한 분기다. 특히 원문에 실제 검색어가 있어도 대역이 빈 결과를 반환하는 사례가 있으므로 실제 키워드 실패·벡터 우위를 입증하는 자료로 쓰지 않는다.

#242에서는 같은 데이터셋·원문/RDB 버전·회차 범위·생성 모델·질문으로 RDB/직접 근거만, 원문만, 결합 방식을 비교한다. 사용자 직접 입력처럼 원문에 없는 정보는 가용성이 다른 별도 범주로 비교한다. 답변 가능 질문의 응답률, 사실 정확도, 인용 지지율, 필수 근거 누락, 범위 준수, 지연·실패·호출 수와 전체 비용을 기록한다. 통과 기준은 baseline 뒤 최종 평가 전에 고정하며 결과에 맞춰 사후 완화하지 않는다.

## 사용량과 관측

질문 해석·행/근거 선택·답변의 실제 provider 호출과 각 schema 재시도는 `ChatTextClient`/`Execution.call()`을 사용한다. 질문 embedding은 `ChatEmbeddingClient`의 `CHAT_QUERY_EMBEDDING`으로 예약·정산한다. 검색 준비의 서비스 부담 `OPERATIONAL_BACKFILL`과 혼용하지 않는다. SDK의 숨은 자동 재시도로 원장을 우회하지 않는다.

실제 input/cached/output, 실패·절단 사용량, UNKNOWN과 예약 복구 계약을 유지한다. cached input은 input의 일부이며 UNKNOWN은 0토큰이 아니다. 질문별 비용 감사의 기준은 실행 원장이다. 검색용 Prometheus의 provider 응답 token counter만으로 실패·UNKNOWN·지연 정산을 포함한 최종 비용을 대신 계산하지 않는다. 검색 방식/라운드/도구 수, 반환·사용 근거 수, 문맥량·단계 지연·실패 이유는 전체 질문 ID와 연계해 조사할 수 있어야 하지만 고유 ID·질문·원문·답변을 metric label로 사용하지 않는다. 조회 상한과 전체 실행의 모델 호출/누적 예약 예산을 각각 지켜야 한다.

모델/embedding의 호출 counter와 provider latency는 예약이 통과한 뒤 실제 provider delegate를 호출하는 경계에서 측정한다. 예약 거절을 provider 호출로 세지 않고 provider latency에는 예약 대기 시간을 포함하지 않는다. cached-input token과 제한된 reason 분류를 별도로 기록하며, UNKNOWN이나 정산 지연이 있는 원장의 비용을 이 counter만으로 확정하지 않는다.

별도 `Chat retrieval trace`는 내부 attempt ID에 계획의 경로/요청 수/사건 문맥 유무, 검색 방식·라운드·후보 청크 ID/순위/점수, 선택한 E 참조와 청크 ID, 제외 사유, 입력 한도 적용 뒤 실제 제공한 참조, 답변 coverage·미확인 요청 참조와 최종 선택 근거를 연결한다. `published` 단계 로그도 후속 결과 저장 성공을 뜻하지 않으므로 실행 원장과 결과 상태를 함께 확인한다. 이 메타데이터는 원래 실행의 모든 모델 출력을 재생하는 기록이 아니다. 원시 질문·원문·모델 답변·사건 문맥 설명·회원/작품 ID·인증값을 저장하지 않고 고유 ID를 metric label로 사용하지 않는다.

## 실행 설정

환경변수는 프로세스에 명시적으로 전달한다. `HybridSettings`는 분석 `.env`를 자동으로 읽지 않는다. Python QA도 활성화된 상태에서 hybrid를 선택하며, 비활성 기본 경로는 기존 RDB handler다.

| 변수 | 기본값 | 의미 |
|---|---|---|
| `CHAT_RETRIEVAL_ENABLED` | `false` | hybrid handler 사용; `CHAT_QA_ENABLED`도 필요 |
| `CHAT_RETRIEVAL_DATABASE_URL` | 빈 값 | 검색 전용으로 명시한 사설 DB 연결; 비밀값 출력 금지 |
| `CHAT_RETRIEVAL_EMBEDDING_VERSION` | `v1` | Python 검색과 Java 인용 검증이 공유하는 임베딩 버전 |
| `CHAT_RETRIEVAL_KEYWORD_TOP_K` / `VECTOR_TOP_K` | `12` / `12` | 라운드별 검색 결과 상한 |
| `CHAT_RETRIEVAL_NEIGHBOR_RADIUS` / `MAX_NEIGHBORS` | `1` / `6` | 인접 범위와 반환 수 상한 |
| `CHAT_RETRIEVAL_MAX_EVIDENCE` / `PER_EPISODE` | `8` / `3` | 최종 자료 수와 검색 회차별 상한; 직접 근거도 전체 개수에 포함 |
| `CHAT_RETRIEVAL_EVIDENCE_TOKENS` | `6000` | 직접 인용과 검색 문맥의 본문 토큰 상한; 겹친 검색 slice는 병합 후 계산 |
| `CHAT_RETRIEVAL_MAX_ROUNDS` | `2` | 키워드 다음 벡터까지의 최대 검색 라운드 |
| `CHAT_RETRIEVAL_MAX_MODEL_CALLS` | `6` | 계획·선택·답변과 schema/참조 오류·출력 절단 복구를 포함한 모델 호출 상한 |
| `CHAT_RETRIEVAL_MAX_QUERY_EMBEDDINGS` | `1` | 질문 embedding 호출 상한; 0이면 벡터 단계를 생략 |

표의 `VECTOR_TOP_K` 같은 축약된 두 번째 변수에도 `CHAT_RETRIEVAL_` prefix가 붙는다. 기존 `CHAT_QA_MAX_TOOL_CALLS=16`과 서버 실행의 도구 한도 중 작은 값을 적용하고, 검색·인접·receipt·재검증도 예산에 포함한다. 모델/embedding 호출은 실행의 전체 호출·누적 예약 토큰 한도 안에서도 제한된다. 직접 인용과 검색 본문은 같은 6,000토큰 상한을 사용한다. prompt·질문·행·schema는 별도이므로 전체 `CHAT_QA_MAX_INPUT_TOKENS=32000`와 문자 상한도 검사한다. 이전에 유지한 검색 청크와 새 후보도 함께 병합해 겹침을 두 번 세지 않는다. 위 값은 초기 설정이며 품질/비용의 실측 최적값이 아니다.

단계별 출력 기본값은 해석 2,000·답변 6,000, provider가 출력 절단으로 분류한 경우의 확대 상한은 7,000이다. `CHAT_QA_MAX_ATTEMPTS=2`는 최초 호출과 모든 종류의 재시도가 공유한다. 복구도 새 호출 예약·정산을 거치며 잘린 JSON을 이어 붙이지 않는다. Spring 누적 예약 기본값 `CHAT_ATTEMPT_TOKEN_BUDGET=240000`과 맞춘다. 입력 32,000·확대 출력 7,000을 텍스트 여섯 호출 모두에 보수적으로 적용하고 질문 임베딩 예약 4,256을 더한 238,256은 예산 설계용 상한이며 평균 또는 실제 사용량이 아니다. 상세는 [단일 질의응답](chat-qa-v1.md)과 [실행 계약](chat-execution-v1.md)을 따른다.

- 계획 v16·결합 답변 v20·원문 전용 답변 v7를 사용한다. 원문 전용 schema는 존재하지 않는 등록 행/항목 배열을 빈 값으로 제한한다.
