# 3단계 착수 명세: 같은 관계 의미를 두 방식으로 읽고 비교하기

상태: **3단계 구현·비교 실험으로 이어진 착수 명세**. 아래 본문은 1·2단계에서 합의한 계획을 보존한다. 후속 [Java #442](https://github.com/catchhole-soma/catchhole-backend-java/issues/442)의 실제 구현·명령은 [실행 안내](relationship-semantics-experiment.md), 검증 결과·비용·채택 판단은 [비교 보고서](evaluations/relationship-semantics-comparison.md)를 따른다. 본문의 ‘아직’, ‘다음’은 이 명세를 작성한 시점의 표현이다.

- 추적: [Java #438](https://github.com/catchhole-soma/catchhole-backend-java/issues/438)
- 목적/선택 기준: [관계 의미 모델 설계](relationship-ontology-plan.md)
- 주 입력: [일반 관계 fixture 계약](relationship-semantics-fixtures.md), [합성 JSON](../tests/fixtures/relationship_semantics_cases.json)
- 회귀 자료: [가족 fixture 계약](relationship-ontology-fixtures.md). 3단계에서 조부모를 계산하지 않는다.

## 1. 다음 작업을 한 문장으로

**같은 합성 입력을 일반 Python 공통 모델(B)과 RDF 모델(C)로 각각 읽고, 방향·축·상태·회차·근거를 잃지 않고 같은 질문에 답하는지 비교한다.**

목표는 “RDF 파일을 만들었다”가 아니라, 표준 도구가 B보다 실용적인 이점을 주는지 판단할 자료를 남기는 것이다. 현재 계약을 그대로 재사용하는 A의 가능성도 함께 검토한다. A는 1·2단계에서 조사한 기존 구현이며 이번 fixture를 이미 실행한 baseline이 아니다.

## 2. 시작 전에 확인할 입력

1. 기존 이슈/PR의 최신 커밋과 이 명세를 확인한다. 다른 작업 브랜치의 변경을 섞지 않는다.
2. 두 fixture 무결성 검사를 실행한다. 실패하면 3단계 결과를 만들기 전에 자료 오류를 해결한다.
3. 일반 관계 10사례·11질의에서 `claims`, `facts`, `suppressions`, `queries`가 각각 다른 책임임을 확인한다.
4. 입력 로더가 `expected`와 `consumerExamples`를 읽지 않도록 분리한다. 질의 입력에는 query의 mode/cutoff/context만 넘기고 수작업 정답은 평가기가 별도로 읽는다.
5. 같은 파일에서 정답 필드를 제거한 복사본을 사용해도 실제 결과가 같아야 한다. 정답을 보고 결과를 복사하는 구현을 막는 회귀를 둔다.

현재 자료는 LLM 출력이나 Java DTO의 직접 복사본이 아니다. 원문의 해석·주장 상태·관계 tuple은 수작업으로 고정했다. 실제 관측의 양 끝점 순서가 관계의 의미 방향과 같다고 가정하지 않는다. 실제 adapter는 5단계에서 명시적으로 설계한다.

### 관계 갱신·종료를 별도로 검증하기

현재 10사례·11질의는 수작업 snapshot의 의미를 비교하는 자료다. 최종 `ENDED` 한 행의 조회 성공만으로 `ADD → UPDATE → END → 재개(UPDATE)`가 제대로 저장·조회된다고 판단하지 않는다. 아래 항목은 추가로 고정할 재현 입력과 완료 기준이며, 현재 fixture 검사 50개가 전체 상태 전이를 실행했다는 뜻은 아니다.

- 같은 관계의 설명 갱신·종료·재개가 회차별 이력과 근거를 보존하는지 확인한다. 종류·방향이 다른 관계로 바뀌면 기존 slot의 종료와 별도 slot의 추가를 구분한다. 다른 slot의 추가만으로 기존 관계를 자동 종료하지 않는다.
- 새 회차에서 관계가 언급되지 않았다는 이유만으로 종료하지 않는다. 명시적인 종료 근거를 얻었는데 추출·인물 해소·판단·저장·조회 중 어느 단계에서 놓쳤는지는 따로 추적한다.
- 별칭이 동일인물로 확정되어 같은 slot으로 모이면, 비교 문맥과 공개 조회가 같은 최신 상태를 선택하는지 확인한다. 예전 별칭의 ACTIVE와 새 이름의 ENDED가 함께 남는 경우를 포함하며, 사용자 정정·삭제 억제와 근거를 잃는 단순 중복 제거로 대체하지 않는다.
- 잘못 추출한 기록의 정정을 서사 속 종료로 바꾸지 않는다. 사용자 삭제 억제를 재분석·새 근거·별칭 병합으로 우회하지 않는다.
- 읽은 회차 이후의 변경·종료 근거를 노출하지 않는다. 필요한 이력이 없으면 과거 상태를 발명하지 않고 미지원으로 표시한다. 기존 GH367의 회차별 독립 이력 정책도 유지한다.
- 후속 추론 단계에서는 마지막 유효 전제가 철회되면 파생 관계를 철회하고, 다른 독립 근거가 남으면 그 근거가 지지하는 결론은 유지한다. 이는 3단계에서 새 추론기를 구현한다는 뜻이 아니다.

실제 원문에서 모델이 필요한 `END`를 선택하는지는 별도의 자연어 평가 대상이다. 구조검증 통과나 수작업 `END` 응답의 전달 성공을 모델 정확도의 근거로 쓰지 않는다. RDF·SHACL 도입 자체도 갱신·철회 처리나 자연어 이해를 자동으로 보장하지 않는다. 기존 코드에서 재현한 결함은 별도 수정으로 추적하고, 그 수정 효과를 RDF의 도입 효과로 계산하지 않는다.

정확한 디렉터리 구성은 구현 시 기존 프로젝트 관례에 맞춰 조정할 수 있다. RDFLib·pySHACL은 C의 실험 의존성 후보이며 버전과 지원 범위를 기록한다. OWL reasoner, 그래프 DB, 외부 서비스는 3단계에 필요하지 않다. 패키징/의존성을 바꾸면 AGENTS.md의 설치 검증을 따른다.

## 4. 구현 순서

### 3-A. 실제로 공유할 수 있는 정보부터 고정

작품·노드·출처·주장·확정 slot·수명·억제·조회 범위를 B에 담는다. 원래 axis/kind/direction과 source/target을 보존한다. MUTUAL/UNDIRECTED의 동일성은 대칭이지만 원본의 필드 값을 임의로 덮어쓰지 않는다.

원문 해석이나 CONFIRMED 판정은 입력값이다. 입력 구조 검사와 도메인 의미 해석을 혼동하지 않는다. 지원하지 않는 STORY_TIME 질의와 재구성할 수 없는 과거 상태는 명시적으로 실패/미지원으로 보존한다. 최종 ENDED 한 행으로 예전 ACTIVE 상태를 발명하지 않는다.

### 3-B. 일반 코드로 기준 실행 만들기

B가 합성 입력에서 질의 결과를 계산한다. 포함된 fact의 전체 tuple·상태와 근거 claim/source 참조를 반환한다. 제외/보류/미지원 이유도 별도 필드로 보존한다. 사용자 삭제 억제는 원문 검색 전체를 금지하는 기능이 아니라, 공유 확정관계 조회에서 해당 slot을 되살리지 않기 위한 제안 계약이다.

B는 기존 Java 실행 결과가 아니다. B의 결과를 “기존 시스템 정확도”라고 기록하지 않는다. A에 대한 판단은 기존 계약이 이 의미를 이미 지원하는지와 필요한 연결 비용을 조사한 근거로만 한다.

### 3-C. 동일한 의미의 RDF 표현 만들기

C는 인물 간 선만 저장하지 않고 Claim/Relation fact와 Source, Query context, Suppression의 연결을 보존한다. 이 자료는 관계 자체에 메타데이터가 필요한 모델이다. 전역 `A trusts B`만으로 축약해 추측·정정·공개 회차를 버리지 않는다.

필수 필드·자료형·참조와 허용 구조는 SHACL로 확인한다. OWL의 domain/range 선언을 폼 검증처럼 오해하지 않는다. 같은 인물 ID를 사용하고 이름으로 `owl:sameAs`를 만들지 않는다. RDF 출력에서 다시 읽은 tuple·상태·근거가 B 입력과 같아야 한다.

질의/회차/억제 정책 중 일반 코드가 담당하는 부분과 RDF 질의/shape가 담당하는 부분을 명시한다. C에서도 도메인 조건문이 필요할 수 있으며 이를 감추지 않는다. 무조건 조건문 수가 적어야 성공인 실험이 아니다.

### 3-D. 같은 질문을 실행하고 보고하기

구현 초반에 B/C가 반환할 공통 결과 형식을 먼저 고정한다. run 메타데이터에는 구현 종류·코드 SHA·입력 hash·환경을, 각 질의에는 `caseId`, `queryRef`, `status`, `reason`, 실제 facts의 전체 slot·상태·지식 회차·근거 참조, 제외 사실과 사유, 보류 claim 참조를 담는다. `expectedText`는 실행 결과에 넣지 않는다. case/query/fact 참조는 집합으로 비교하되 중복은 오류로 처리한다. 근거 참조는 순서와 무관하게 비교하고, DIRECTED의 source/target 순서는 유지한다. MUTUAL/UNDIRECTED의 대칭성은 비교 키에만 적용하고 입력의 필드 값을 덮어쓰지 않는다. 정렬은 보고서의 재현성을 위한 것이며 의미를 바꾸는 정규화로 사용하지 않는다.

B/C 모두 실제 결과를 저장한 뒤 정답과 비교한다. 11질의 각각의 지원 상태, 포함/제외 사실, 전체 tuple·상태·출처, 보류 지칭을 비교한다. facts ID만 같은데 의미 필드가 달라진 경우도 실패다. 수작업 소비자 예시의 문장은 설명 자료이며 문자열 일치로 자연어 품질을 채점하지 않는다.

세 소비자의 예시는 같은 범위에서 쓰는 의미의 계약이다. 로컬 wrapper 세 개가 같은 배열을 돌려준다는 사실만으로 검색·검수·관계도 통합 효과를 입증했다고 하지 않는다. 실제 소비자 연결은 5단계 이후다.

## 5. 공통화와 표준 도구의 차이를 확인할 작은 변경 실험

기본 사례를 통과한 뒤 동일한 두 변경을 B/C 양쪽에 적용한다. 측정용 추가 사례는 원래 정답을 덮어쓰지 않고 별도로 남긴다.

1. 현재 제품 enum에 있는 `AFFECTION`의 명시적인 한 조합을 추가한다. 축/방향을 전역 고정하지 않는다. 새 감정 slot을 지원하는 데 바꾼 모델·query·consumer 변환·검사 지점을 기록한다.
2. 같은 데이터에서 “A→다른 사람의 ATTITUDE”와 “다른 사람→A의 ATTITUDE”를 분리하는 질의를 추가한다. 새 자연어 해석은 고정 입력으로 제공하고, 어느 쪽이 기존 모델/질의를 재사용했는지 기록한다.

수정한 파일·규칙·매핑과 실제 diff를 남긴다. B도 데이터 주도 공통 모델이면 충분히 같은 수준으로 재사용할 수 있다. 그 경우 C의 도입 근거가 늘었다고 주장하지 않는다. A의 기존 계약에 이미 가능한 조회인지도 문서 근거와 함께 표시한다.

## 6. 완료 조건과 결과 형식

| 확인 항목 | 완료 기준 |
| --- | --- |
| 독립 실행 | 모델·DB·네트워크 없이 같은 명령으로 B/C 실행 가능 |
| 정답 분리 | loader/실행은 expected 미접근, 평가기만 읽음. 정답 삭제/변조가 실제 결과를 바꾸지 않음 |
| 범위 보존 | 10사례·11질의의 기대 tuple/상태/근거·보류·미지원과 실제 출력이 일치 |
| 금지 결론 | 잘못된 방향·미래 정보·친구 승격·삭제 부활 없음 |
| RDF 왕복 | 지원 필드가 RDF 왕복 과정에서 손실되지 않음. 미지원 필드는 명시적 거절 |
| 비용 근거 | 입력 크기·환경·의존성·로딩/검증/조회 시간을 B/C 같은 조건에서 기록 |
| 변경 근거 | 두 추가 실험의 실제 diff와 재사용/중복 지점 기록 |
| 판정 | A 재사용 / B 공통화 / C 추가 검토 / 근거 부족 중 하나와 이유를 기록 |

최종 보고서는 각 항목에 `미실행/실패/성공`을 구분한다. 속도는 같은 환경에서 준비·검증·질의를 분리해 기록하고 최초 로드와 반복 조회를 구분한다. 작은 합성 자료의 실행 시간을 운영 지연으로 일반화하지 않는다. 비용 허용 범위가 없으면 운영 도입 승인을 대신하지 않는다.

C가 B보다 추가 이득을 보이지 못해 **B 또는 A를 선택하는 결과도 완료**다. 이 단계가 끝났다고 서비스에 온톨로지가 적용되거나 실제 챗봇·검수 품질이 개선된 것은 아니다. 다음 단계는 결과에 따라 제한된 추론 비교를 할지, adapter만 만들지, 현재 구현을 유지할지 결정한다.
