# 세계관 설정의 일반 검토

관련 변경: [Java #180](https://github.com/catchhole-soma/catchhole-backend-java/issues/180).

AI가 대상을 연결하고 기존 항목을 비교했더라도, 같은 대상을 설명하는지 또는 내용을
어떻게 반영해야 하는지 확실하지 않을 수 있다. 이전 계약에는 범위 문제에 대한 검토만
있어 이런 불확실성을 맞지 않는 범위 사유로 표현하면 검증 재시도 후 실패로 남았다.

이제 모델은 `REVIEW_REQUIRED + GENERAL_UNCERTAINTY`를 명시적으로 반환할 수 있다.
예를 들어 전체 종류와 특정 하위 종류를 같은 대상으로 봐도 되는지 확실하지 않다면,
일반 검토로 남기고 “어떤 대상을 설명하는지 확인이 필요합니다”라고 설명한다.
단순히 항목 이름이 다르다는 이유로 검토하지 않고 실제로 불확실한 내용을 설명해야 한다.

## 저장 계약

- 단건, 기존 확정 설정 기반 batch, 순차 batch에서 같은 사유를 사용할 수 있다.
- batch에서도 후보 하나마다 별도 검토 결과를 반환한다. 서로 다른 원본 주장을 합치지 않는다.
- 기존 대상이 하나로 연결된 batch는 그 대상 참조를 유지한다. 이는 비교한 대상의 기록이며
  동일한 대상이라는 사실이 확정된 것은 아니다.
- 기존 항목 참조는 선택 사항이다. 제공했다면 대상과 항목이 실제 비교 입력에 있어야 한다.
- 검토 결과로 기존 항목을 이동·수정·추가하지 않는다. 제안 경로와 값은 후보 원본으로 복원한다.
  한 후보에 여러 추출값이 통합되어 있다면 전체 원본 문자열을 보존한다.
- Spring은 자동 반영 대신 검토 대상으로 남기며, 다음 회차에는 원래 주체·경로·값을
  미확정 참고로 전달한다. 확정 사실이나 선택 가능한 새 주체로 승격하지 않는다.

`SCOPE_UNRESOLVED`와 `SCOPE_MISMATCH`의 기존 조건은 유지한다. 잘못된 scope 사유,
없는 대상·항목, 여러 원본을 합친 일반 검토, 이동 시도는 여전히 검증에서 거절된다.
코드가 잘못된 응답을 자동으로 일반 검토로 바꾸지는 않는다. 재시도에서는 두 사유의 차이를
안내하고 모델이 올바른 판단을 다시 반환해야 한다.

## 적용과 한계

Spring의 새 사유/API·DB 검증을 먼저 배포한 뒤 AI를 적용한다. AI 캐시는 단건 `v11`,
batch `v8`, 순차 추가 지침 `ordered-provisional-v6`으로 구분한다. 과거 실패 후보를 변경하거나
완료 회차를 재분석하지 않는다. 이 변경은 주체 연결 정확도 자체를 개선하거나 기존의
과도한 주체 병합을 복구하지 않는다. 확실하지 않다고 판단한 경우의 표현과 저장 계약이다.

검증은 합성 응답과 로컬 테스트 DB로 수행한다. 실제 작품의 정답지 기반 정확도·재현율은
미측정이며 [v0004 상세](ai-logic-versions/details/v0004.md)에 실행 조건과 한계를 기록한다.
